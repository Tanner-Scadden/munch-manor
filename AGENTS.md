## Project Notes

A pixel-art zombie shooter, live at https://munchmanor.com (the old `workers.dev` address keeps serving the same build: see "Two origins" in `PLATFORM.md`). It runs on desktop and on phones. The vision, the decided choices, and the roadmap are in [`GAME_DESIGN.md`](./GAME_DESIGN.md): read its "Decided" section before changing how the game plays. Co-op is planned in [`MULTIPLAYER.md`](./MULTIPLAYER.md). The story, and the escape the manor direction being brainstormed, are in [`LORE.md`](./LORE.md). The Cloudflare side (hosting, analytics, the on-device SQLite save, and sync) is in [`PLATFORM.md`](./PLATFORM.md). Before you finish a change, run `typecheck`, `lint`, `test`, and `build`. All four must pass. Also run `test:full` when the change touches gameplay (`simulation.ts`, `waves.ts`, `pacing.ts`, `combat.ts`, the zombie, boss, or trap modules), since CI runs it and blocks the deploy on it.

**Go easy on the laptop.** One 12-core laptop often runs several agents at once. Two agents running 8-process balance batches together pushed the load average to 30 and made every step about three times slower.

- Run every heavy job through the guard: `bun run balance`, `bun run perf:check`, or `bun run heavy -- <command...>` for anything else heavy, such as an audit or a shots script. Never call `tools/balance/simulate.ts` or a heavy audit directly.
- The guard aims at about 70% of the machine: a 1 minute load near 0.70 x cores (8.4 on 12, `HEAVY_TARGET_LOAD` to change it). A job starts only when the load, the jobs started in the last minute, and its own cost fit under that target.
- **Timing** jobs (`perf:check` and the timing audits, `splash.ts`, and any command it does not know) run alone. **CPU** jobs (the balance bot, nightly, wave snapshots, determinism) run one at a time beside audits and size their `WORKERS` to the budget, up to 8. **Shared** jobs (the shots scripts, `taps.ts`, and the other screenshot and functional audits) run up to 4 at once, each costing about one core per browser context. `--timing`, `--cpu`, or `--shared` before the command overrides the class.
- **Long jobs yield.** The balance bot plays its runs in chunks of about 25 (a wave pass by snapshot slot), the nightly yields between its jobs, `splash.ts` between profiles, and `perf:check` between scenarios. At each boundary the guard hands over to any waiting job and queues again, so nobody waits long behind one batch. Results are the same as one unchunked run. A new long script should do the same with `yieldTurn` from `tools/heavy/turn.ts`.
- **The queue goes round by worktree.** A worktree that just had a turn goes behind other worktrees' waiting jobs; otherwise jobs go by arrival. A Shared job may start ahead of a Timing or CPU job that only waits for a running CPU job (backfill).
- **A solo turn is a 10 minute lease** (`HEAVY_LEASE_MINUTES`). A job past it keeps running, but the guard says so loudly and waiting jobs name it: split such a job so it yields.
- `bun run test` sizes vitest's workers to what is left of the budget (at least 2) and counts itself, so test runs from several agents share the target. CI is unaffected.
- The guard refuses a sixth balance batch per branch without `--allow-more` (`bun run heavy -- --reset-budget` starts the count again). How it works is in [`tools/heavy/README.md`](./tools/heavy/README.md).
- Cap tuning at about three batches per change. Use 100 runs to sort ideas and 200 only to confirm the final numbers. Results within a few points of a target are fine: list misses as follow-ups instead of running more batches.

**Check balance in tiers**, cheapest first, as "How balance is checked" in `GAME_DESIGN.md` describes: `bun run test` (the model's guardrails) on every change, `bun run test:full` (also the wave 2 snapshot smoke pass), `bun run balance -- --wave N --runs 100` while tuning a wave, and `bun run balance:nightly` once a change is done. A guardrail not met yet is a `test.todo` in `tools/balance/model.test.ts`; flip it to `Met` once a change brings it in. Rewrite `tools/balance/baseline.json` (`bun run balance:nightly -- --update-baseline`) only in a change that means to move the numbers, and say so in the commit body.

### Where things are

`src/` is in layers, top to bottom: `app/` (the root's wiring) over `screens/` (one folder per screen, putting features together) over `features/` (one folder per thing on screen) over the shared client layers (`ui/`, `domain/`, `render/`, `art/`, `audio/`, `input/`, `platform/`) over `world/` (the rules the co-op room runs) over `shared/`. Imports point only down ("Folders"). Paths in each table are under its heading's folder. Tests are not listed: each sits in a `__tests__/` folder beside the code it tests ("Folders" below). The API Worker is in `infra/worker/` (analytics, and sync's Durable Objects in `sync.ts`), the analytics report and smoke test in `tools/analytics/`, and the SQLite wrapper and sync engine in `packages/`.

### Folders

`src/` is in folders by layer (the file tables above). `tools/lint/folders.ts` (in `bun run lint`) fails a file straight in `src/` or in a folder that is not a layer, and `munch/folder-imports` fails an import across the lines below.

- **The layers, top to bottom, one way.** `app/` (the root Block's wiring) over `screens/` (one folder per screen) over `features/` over the shared client layers, `ui/`, `domain/`, `render/`, `art/`, `audio/`, `input/`, and `platform/` (one layer: they import each other freely, short of a cycle) over `world/` over `shared/`. `munch/folder-imports` fails an import of a higher layer, an import of one screen from another, and an import of one feature from another, as in Feature-Sliced Design (its widgets and pages are our screens).
  - **`app/`** is the root's wiring only: the Model, the Bindings and Composition, Commands, Mounts, Subscriptions, the root view that places each screen, the root's own Dialogs (each shell around the insides its screen draws), and every root handler in `app/update/` with the Steps they share, a plain feature's too (`home.ts`, `end.ts`, `onboarding.ts`). Anything that needs a Binding, a Mount, or a root Step stays here; a screen gets it handed in (the menu panel takes the Munchopedia's view, the end card's SHARE takes the ShareFromClick Mount).
  - **`screens/`** puts several features together into one screen: `screens/home/` (the home menu, its hand and panels, the install tile, the update gift) and `screens/game/` (the game surface in every phase: the world scene, the HUD, the overlay, the touch controls, Rattles' bubble, and the buttons over the game). A screen imports any feature and any lower layer. A new screen is a new folder; what two screens both need goes down to a feature or a shared layer.
  - **`features/`** is one folder per thing on screen, apart from the others.
  - What two features both need goes down to the layer they share: a client rule or Schema to `domain/`, an HTML part to `ui/`, canvas drawing to `render/`, pixel art to `art/`, the store and sync to `platform/`, a pure helper to `shared/`.

  The rule has two exceptions, each listed in it with its reason:
  - **The root's types.** `import type` of exactly the root's `Model` (`app/model.ts`) and its view builder (`ApplicationViewBuilder` and `ApplicationAttribute` in `app/composition.ts`), never a value and never another name from those modules: a feature's rules and views, and the client layers' drawing, read the root's one Model, and a view sends the root's Messages. In November 2026, when the rule came in, 57 imports were `type Model` this way and 14 the view builder (15 of the 71 from `screens/`); 6 more were narrowed to the `World` they read (the kitchen's art, traps, effects, the laser sight). Narrow a function to `World` or to the fields it reads where that is honest, rather than adding to them.
  - **A parent Block and its child.** A feature imports another only as a parent Block importing the contract of a child it binds: the child's `block.ts`, `layer.ts`, `model.ts`, `message.ts`, and `inMessage.ts`, straight in its folder (FOLDKIT.md "File organization"). The pairs are the rule's `CHILD_BLOCKS`: the solo lobby and co-op bind the hero picker (`heroes`), and the Munchopedia binds the guide to the house's finds (`guide`). A child's own children in its `blocks/` folder are the same feature (the Profile's Look tab). A new pair joins the list with its reason; anything else a parent needs of a child (an id its opener wears, a picture) moves into the child's contract or down a layer.

  Before the rule, 181 imports went up a layer (79 of them types only) and 142 between sibling features. They were fixed by moving code as it was: the features' handler modules up into `app/update/` (`home.ts`, `end.ts`, `onboarding.ts`, `coopPlay.ts`), the views that put features together up into `screens/` (`screens/game/worldView.ts`, `screens/game/hud.ts`, `screens/home/homeView.ts`, ...), the client rules and Schemas several features read down into `domain/`, the HTML parts into `ui/`, feature art into `art/` and `render/`, and the co-op lobby's Replica into `platform/`.

- **A root Message and its handler go with the feature that sends it.** The root's Message union in `app/message.ts` is one flat `defineMessageUnion` of every group's cases, so `Message.X(...)`, the generated `Got*` envelopes, the save, and the tools see one union as before. A group is a cases record and its own union in the sending feature's `message.ts` (`inputCases` and `InputMessage` in `src/input/message.ts`, `homeCases` and `HomeMessage` in `src/features/home/message.ts`; the browser's and the Worker's in `src/platform/message.ts`), and that feature builds and types its Messages from it (`HomeMessage.ClickedPlayButton()`). A new root Message joins a group (or a new group, spread into `app/message.ts` and listed in `src/app/__tests__/message.test.ts`, which fails a tag two groups both name). Its handler joins that group's `defineHandlers({...})` record (`src/app/update/step.ts`) beside the Steps it calls, in `src/app/update/`, since a handler calls the root's Steps and a feature imports nothing of `app/`: a feature's own in `app/update/<feature>.ts` (`homeHandlers` in `home.ts`, `endHandlers` in `end.ts`, `onboardingHandlers` in `onboarding.ts`), the rest by what they handle (`inputHandlers` in `input.ts`, `saveHandlers` in `save.ts`, ...), and one that opens a child Block in that child's `app/update/<child>.ts` (`lobbyHandlers`, `coopHandlers`). `app/main.ts` spreads every record into its one exhaustive `makeUpdate`, so a Message with no handler fails typecheck there.
- **`src/world/` is what the co-op room loads.** It imports only `src/world/` and `src/shared/`, Effect, Foldkit's `struct` and `schema` modules, and the netcode package's types; `src/shared/` imports only itself (`munch/folder-imports`). `bun run world:check` fails any game module outside those two folders in the room's bundle, and in infra's types but for the two infra serves (`INFRA_OWN_MODULES`). A rule the room runs goes in `world/`; a client rule, view, or Step goes in a client folder. Name a feature's folder after its `world/` folder where both exist (`world/shop` and `features/shop`, the hold to buy and its tags).
- **One folder per thing on screen** in `features/`: its view, styles, and client rules, and a Block's own update. A plain feature's Steps on the root Model and its handlers live in `app/update/<feature>.ts`. A new feature is a new folder.
- **A folder that holds a Block uses Foldkit's file names**, as in `repos/foldkit/examples/workspace/src/blocks/*`: `block.ts` (`Block.make`), `layer.ts` (its `makeLayer`), `composition.ts`, `message.ts`, `model.ts`, `update.ts`, `view.ts`, `inMessage.ts`, `inMessageUpdate.ts`, and `__tests__/` with `story.test.ts` and `scene.test.ts`. A Block's child Blocks go in its own `blocks/` folder (FOLDKIT.md "File organization"). The root's Steps that drive a child Block (its OutMessage folds) live in `app/update/<child>.ts` (`coop.ts`, `profile.ts`, `lobby.ts`), not in the child's folder. Co-op (`features/coop/`) is the model. The Profile (`features/profile/`) shows a child with its own children: its tab strip and the Look tab (`features/profile/blocks/look/`), its Steps shared by its update, InMessages, and folds in `steps.ts`. The hero picker (`features/heroes/`) is one Block bound in two parents, the solo lobby (`features/lobby/`) and co-op, so it stays a sibling folder rather than either one's `blocks/`, and the guide (`features/guide/`), bound by the Munchopedia (`features/munchopedia/`) on its Finds page, keeps its own folder too; each parent's Bindings sit in its own `bindings.ts`, apart from the folds in `composition.ts`, so the Steps that call a Binding import no cycle. Add no `index.ts` barrel beyond co-op's. The root itself still has its older names (`definition.ts` for the Block, `block.ts` for its Layer, `layer.ts` for its handlers): see "Follow-ups".
- **Tests sit in `__tests__/`** in the folder that holds the code they test (`src/world/keys/__tests__/keys.story.test.ts`), with the fixtures only that folder's tests use (`boss.fixture.ts`). This departs from FOLDKIT.md's "beside the code under test" on purpose, so a folder lists its modules first: follow this file. Setup several folders' tests share lives in `src/test/`. Shipped code never imports `src/test/` or a `__tests__/` folder (`munch/folder-imports`), and a module that is not a test or a fixture never sits in `__tests__/` (`tools/lint/folders.ts`). The rule covers `src/` only: the packages keep their `test/` folders and the tools their tests beside their scripts.

### Rules

- **Keep the game deterministic.** `update` is pure. It never calls `Math.random` and never reads the clock. Randomness comes from the seeded generator whose state lives in the Model, so the same seed and the same Messages give the same game.
- **Support desktop and touch.** Every input must work with a keyboard and mouse and with touch. Touch tracks each finger by its `pointerId`, so two thumbs work at once.
- **Buttons act on OnClick.** `src/input/touchTaps.ts`, mounted on the game's root, turns each finger's tap into a click from its own pointer events, so a button works with another finger on the glass and acts once. Never act on a touch or mouse release (`munch/tap-by-click`); `OnPointerDown` is for acting the moment a finger lands. An animation never moves a button or what holds one: it fades or flashes in place, and only art inside moves (`src/app/__tests__/motion.test.ts`).
- **Support portrait and landscape on phones.** A touch phone held upright plays in the portrait layout (see "Portrait play" in `GAME_DESIGN.md`). Overlay code reads the screen from `screenOf(model)`, never `VIEW_WIDTH` and `VIEW_HEIGHT`, and CSS reads `--screen-w`, `--screen-h`, `--world-top`, and `--frame-top` (the top of the banners' frame) from `.game-root`, with `[data-layout='Portrait']` rules for portrait. Check a layout change with `tools/audit/shots34.ts` and `PORTRAIT=1 bun taps.ts`. The installed Android app starts in landscape and turns only when Settings' ROTATE is on (see "Rotation" in `GAME_DESIGN.md`).
- **Follow the design doc.** Choices under "Decided" in `GAME_DESIGN.md` are settled. The "Reference notes" are ideas, not decisions. If a change goes against a decision, say so before making it.
- **Show, don't explain.** Fewer words, more visuals. Prefer icons, art, motion, and sound to text, keep every label and line short, and never repeat what a player has already seen. Write new copy that way, and trim old copy you touch. See "Show, don't explain" in `GAME_DESIGN.md`.
- **Use original art and names.** Do not copy art, names, or item lists from Zombie Estate 2.
- **Use Effect fully.** Reach for Effect's own APIs (Schema, Match, services, resources, `effect/sql`) rather than working around them. Keep the `@effect/language-service` plugin in `tsconfig.base.json`: without it `typecheck` still passes but reports no Effect problems.
- **Draw fixed art as sprite images.** A pixel map goes through `spriteShapes`, and a fixed list of whole pixel rectangles goes through `bakeShapes`. Build them once at module scope or in a cache, never per frame. A production build packs every sprite into a prebuilt atlas (`tools/sprites/`, see `docs/IMAGES_PLAN.md`), found by content key, so the game draws cropped regions of a few PNG files instead of encoding one per sprite. A sprite built lazily, on first use, must be listed in `src/art/spritePrecompile.ts`, or `tools/sprites/atlas.test.ts` fails. HTML that shows a sprite as an `<img>` takes `standaloneSource(image)`, since an `<img>` cannot crop. Tests draw stand-ins instead of PNGs (`src/test/vitest-setup.ts`). Shapes that change every frame, such as particles, bars, and decals, stay `Rect` shapes.
- **Read the map from the level.** The map is data: the Model's `level` names the level, which hand-made room its run rolled into each slot (`arrangement`, from the seed), and its open exits, and `levelOf(model)` hands back the built `Level` with its tile lookups, doors, thresholds, and spawn doors. Every function that reads tiles, doors, or the level's size takes that `Level`. Only a fresh run (which starts in the parlour) and the stall (which stands there) read `PARLOUR` directly. Tile queries read `level.tileFlags`, one byte per tile (`hasTileFlag`). Tables derived from the map key on the `Level` (a new record whenever an exit opens), as the pathing tables and the room canvas do; the flow field is not kept at all, it is built on the frame.
- **Keep the frame cheap.** `src/render/__tests__/perf.scene.test.ts` budgets the canvas shapes and paint operations of a full room, and `bun run perf:check` gates frame time against a recorded baseline (see `tools/audit/README.md`). In code that runs every frame, check a union's tag with `isAnyOf`, not `guards`: a guard validates the whole value through Schema, and `Phase` carries the wave's spawn list.
- **Persistent data goes through the store.** Anything that must last across reloads goes in `PlayerSave` (its Schemas in `src/shared/playerData.ts`, the rest in `src/platform/save.ts`), with a bump of `SAVE_VERSION` and a migration or a fallback to no save for the older version. Add it to `saveOf` and `restoreSave`. `update` then writes it on change through the `WriteSave` Command, which goes through `PlayerStore` in `src/platform/store.ts`. Never touch SQLite, OPFS, or `localStorage` anywhere else. Other SQLite code goes through `@munch/sqlite-wasm-effect` (see its README).
- **Player data changes go through sync mutations.** The save lives in the player sync scope (`src/platform/playerScope.ts`): a change to it is a mutation, never a direct write to the `player` or `kills_by_kind` tables. A new kind of change gets a `PlayerChange` case and its place in `changesBetween` (`src/platform/playerSync.ts`), a mutation in `src/platform/playerScope.ts` with a deterministic apply (time only from its context, no randomness, increments rather than totals where two devices can both change it), and its case in `runChange` in `src/platform/storeSqlite.ts`. A new column or table is a new numbered scope migration; never edit one that has shipped, and bump a mutation's `version` when its args change. The same file runs in the sync Worker, so keep it to `effect`, the engine, and `src/shared/playerData.ts`. See "What phase 4 built" in `PLATFORM.md` and `packages/sync-engine/README.md`.
- **Send analytics only through SendRunSummary.** The summary is built in `update` from the Model (`src/platform/analyticsRun.ts`), the network call lives in the Command, and nothing is sent when "Share anonymous play stats" is off. A new field goes in `RunSummary` in `src/platform/analytics.ts` with a bump of `RUN_SUMMARY_VERSION`, and a new D1 migration in `infra/migrations`. Nothing personal goes in a summary.
- **Write tests for game logic** as Story tests that replay Messages. Break the code once to see the test fail before you trust it.
- **Keep `bun run test` fast.** A test that plays more than about one wave of game time, or takes more than 300 ms, goes in a `*.sim.test.ts` file beside its Story test, which only `test:full` and CI run. A file that needs a page (it builds elements, dispatches window events, or uses `localStorage`) starts with `// @vitest-environment happy-dom`; the rest run in plain Node, and Scene tests always get a page. Files share a worker's modules (`isolate: false`), so a test that changes a global (a spy, a stub, `localStorage`) puts it back in `afterEach`. The nightly workflow runs `test:full` in a shuffled order to catch one that does not. See `vitest.config.ts` and `docs/TESTING_PLAN.md`.

### Blocks and Bindings

The root and its children are Foldkit Blocks (see `FOLDKIT.md`, and `repos/foldkit/examples/pixel-art` for a canvas game with dialogs).

- **The root is split by role**, in `src/app/`. `definition.ts` holds `ApplicationBlock` (`Block.make`) and its helpers, `bindings.ts` the Bindings, `composition.ts` their OutMessage folds and `ApplicationComposition` (a fold calls Steps and a Step calls a Binding, so the Bindings sit apart, as FOLDKIT.md's "OutMessage policies" lays out), `main.ts` init and the handler record, `view.ts` the view, `block.ts` the implementation `layer`, `layer.ts` the root's handler Layer, and `services.ts` `ApplicationLayer`. `entry.ts` only starts the Program, `Program.make({ block: ApplicationBlock, layer })`.
- **A child lives on a Model field through its Binding.** Each dialog, the Munchopedia, the Profile, the single player lobby, and co-op is a Binding on the field of the same name, so its Messages arrive as `Got<Field>Message` (`GotLobbyMessage`). Each Binding starts its child from the child's own init, with its id, and the root's init supplies only the root's own fields (`OwnModel`). Never write a child's field from the root: ask through its operations (`LobbyBinding.requestOpen(...)`, `CoopBinding.requestPressKey({ code })`, `CoopBinding.requestKeepTracers(...)`) and answer its OutMessages in the Binding's fold. A child's requests are its `InMessage` union (`defineInMessageUnion`, named `Requested...` or `InformedOf...`), apart from its local Messages, handled by an exhaustive `makeInMessageUpdate` record in the implementation's `inMessageUpdate`; the Binding's methods are generated from it, and a request that may send an OutMessage declares it in the Block's `inMessageOutputs` (co-op's `src/features/coop/inMessage.ts`). A child's OutMessage says what happened (`RolledNameDice`, `ClickedBuyLook`), never `Requested...`. The Profile shows the rest of the contract: it reads the root only through one `ViewInputs` record (`src/features/profile/block.ts`), and anything random it needs the root rolls from its seeded generator and answers with an `InformedOf...` InMessage (`RolledNameDice`, then `InformedOfRolledName`), so the child's update stays deterministic. A child Block's own children are its Bindings in its `composition.ts` (the Profile's `TabsBinding` and `CharacterBinding`) or `bindings.ts` (the lobby's `HeroPickerBinding` and `HeroDialogBinding`, co-op's `HeroPickerBinding`, and the Munchopedia's `GuideBinding`), on its own fields, and join the same list. When a child's rules read the root's data on every Message, the root hands it as update context rather than a copy in the child: the lobby's picks are the root's (`lobbyPicksOf`, LobbyBinding's `delivery.toUpdateContext`, and the InMessage context its Binding methods take after the payload), and each pick goes up as an OutMessage for the root to make. A Binding operation run inside `makeStep` cannot carry an OutMessage: attach one in the handler with `Update.withOutMessage`, or in a fold on the Model a Binding operation takes (co-op's `Connected` in `src/features/coop/steps.ts`). `munch/no-binding-field-write` fails a `modifyFields` that writes a Binding's field in `src` outside tests; a new Binding joins its list. A child Block gets only its own fields; it learns about the root through operations and view inputs.
- **Two kinds of Step.** A plain `UpdateStep` changes only the root and returns root Commands. A Step that calls a Binding operation is built with `makeStep(model => ...)` and returns a deferred Step, usually `Update.combineSteps([...])`; only a handler's own Model (or `makeStep`'s) may run it, never a Model built with `modifyFields` along the way. Use `combine` from `src/app/update/step.ts` for plain Steps.
- **Every change settles once.** The after-message Steps (`afterMessage` in `src/app/update/settle.ts`: music, end focus, rotation, Nightmare, the run count and summary, the save) run once after every dispatch, a child's delivery and its OutMessage fold included: `update` in `main.ts` is `makeUpdate.compose(handlers, ...)`, with `makeUpdate.except` settling every Message but the synced saves and `makeUpdate.on` settling those with `Synced`, from the `{ before }` Model each receives. A handler in the exhaustive `makeUpdate` record (each group's `defineHandlers` record, spread in) and a fold hold only their own change and never settle themselves. Each Step acts on a change between the two Models and reads only the root's fields, so a dispatch that leaves the root as it was costs little and does nothing. A new Message whose change must not be written back joins `SYNCED_SAVES` in `main.ts`.
- **Commands and Subscriptions carry handlers.** A Command is `ApplicationBlock.makeCommand(name, { args, messages, handler: function* () { return args => effect } })` (co-op's `CoopBlock.makeCommand`), defined beside the update that returns it, and its `.layer` joins `CommandsLayer` in `layer.ts` (`AppHandlers` is read off it). A Subscription is a named entry in `makeSubscriptions` with the Messages it may emit. Co-op's own go through `CoopBlock` and co-op's `CommandsLayer`.
- **Tests drive the root through Block-aware Stories and Scenes.** A root test is `it.effect` from `@effect/vitest` returning `Story.story(APPLICATION, Story.given(model), ...steps)` or `Scene.scene(APPLICATION, Scene.given(model), ...steps)`, where `APPLICATION` is `{ block: ApplicationBlock, layer }` from `src/test/testing.ts`. Import the `Story` and `Scene` namespaces from `foldkit` and qualify every step (`Story.message`, `Story.model`, `Story.Command.resolve`, `Scene.click`), as FOLDKIT.md asks; the shared steps in `src/test/testing.ts` (`tick`, `ticks`, `press`, `tap`, `finishSplash`, `writeSave`, `showDialog`, `closeDialog`, `resolveFocusLobby`, `resolveFocusCoop`, `buyAtCounter`, `tapLobbyHero`, ...) are plain step values that work in both forms, and `RootSteps` types a group of them held apart, such as a table's row (`src/app/update/__tests__/seatAction.parity.test.ts`). `src/features/heroes/__tests__/heroBuy.story.test.ts`, `src/features/onlineRun/__tests__/coopAnalytics.story.test.ts`, and `src/world/gear/__tests__/traps.story.test.ts` show the patterns below.
  - **A child or grandchild** gets its own Message by its Binding, `Story.messageIn(LobbyBinding, LobbyMessage.ClickedStartButton())`, or by its Binding path, `Story.messageIn([LobbyBinding, HeroPickerBinding], ...)`, `[ProfileBinding, CharacterBinding, BodyBinding]`; the runner builds the envelopes, and a test never builds one.
  - **Where a Story starts.** `Story.given(model)` from a named Model is the usual start. A startup flow can start with `Story.init()`, which keeps `bootCommands` for the Story to resolve. When a test needs a state no Message reaches (a co-op room's World arriving through its session, a picker holding a stale try-on), it binds a Story's final Model, `const running = yield* Story.story(...)` in `Effect.gen`, changes it, and starts the next Story from that. A helper that reads an outcome maps the final Model, `Story.story(...).pipe(Effect.map(({ bullets }) => bullets))`, rather than pushing from `Story.model` into an outer array, and never calls `update` itself.
  - **Every Story is yielded or returned.** A Story inside `Array.forEach` or `Array.map` builds an Effect that never runs, and its asserts with it: loop with `yield* Effect.forEach(...)`. `munch/no-floating-story` (in `tools/lint/testRules.ts`) fails a Block-aware Story or Scene that is not yielded, returned to `it.effect`, or handed to an Effect combinator: in `Array.forEach`, a plain `test`, or a statement. The Effect language service's `floatingEffect` catches only the statement and `floatingEffectInVitest` the plain `test`; a Story returned from an `Array.forEach` or `Array.map` callback passes both. Each Story acquires the root's graph, about 2 ms, so a seed sweep of a hundred Stories costs a few hundred: keep it under the 300 ms of "Keep `bun run test` fast" (stop at the first seed that shows what it needs, as Glass's sweep in `src/world/run/__tests__/modifiers.story.test.ts` does), or move it to a `*.sim.test.ts`.
  - **Commands.** A Story ends with every Command resolved. `Story.Command.expectExact` checks the pending Commands in any order; `Story.Command.expectExactInOrder` where the order is the behavior (the load bar fills before the splash goes, `src/features/home/__tests__/menu.story.test.ts`). A Command's args are checked whole, `expectExact(SendRunSummary({ summary }))` with the exact value built by a helper (`crewSummary`), or, where a test is about a few of them, read off the pending Commands with `checkPendingArgs(Story.Command.argsOf(WriteSave))(writes => ...)` from `src/test/testing.ts` (Story's own `argsOf`; the save's veteran grant in `src/platform/__tests__/saveRank.story.test.ts`), then resolved.
  - **Scenes** emit through `SCENE_SUBSCRIPTIONS.<entry>`. A child's Message a Scene cannot raise (a Dialog's Escape) is sent by a Story first, and the Scene starts from the Model it returns (`src/features/hud/__tests__/mobileHud.scene.test.ts`). A Message no Subscription emits is a Command's or Mount's result: resolve that.
  - **A child Block's own behavior** is tested Block-aware on its own (`src/features/profile/__tests__/story.test.ts`, with `Story.inMessage`; `src/features/lobby/__tests__/story.test.ts` with its `updateContext` and `inMessageContext`; `src/features/munchopedia/__tests__/story.test.ts` with `Story.messageIn(GuideBinding, ...)`); a Dialog's Commands are `Dialog.test.ShowDialog` and `Dialog.test.CloseDialog`, resolved with `showDialog()` and `closeDialog()`.
  - **`src/app/pureApp.ts` is for the tools**: the balance bot, the determinism tools, the audit harness, and the sprite atlas play the game through its plain `update`. Tests read its `initialModel` (the whole start Model, behind the named Models of `src/test/model.fixture.ts`) and `subscriptions` (`SCENE_SUBSCRIPTIONS`), and nothing else.
  - **No plain Story is left.** Every test that drives the game, `src/world/` and the `*.sim.test.ts` replays and bot sims included, is a Block-aware Story or Scene over `APPLICATION` or a child Block. `munch/no-plain-story` (in `tools/lint/testRules.ts`) fails, in tests and their shared setup, a `story` or `scene` imported from `foldkit/story` or `foldkit/scene`, a `Story.story` or `Scene.scene` over an update function or a `{ update, view }` record, and pureApp's `update`, `view`, or `init` imported as a value. A view of its own over the acquired root is a custom renderer, written inside `Story.withBlock(APPLICATION, block => ...)` as FOLDKIT.md allows (`src/app/__tests__/scene.test.ts`'s document title, which a Block-aware Scene, drawing the document's body only, cannot see). The one plain Scene left, the patched painter on a bare canvas with no game and no Block (`src/art/__tests__/sprite.scene.test.ts`), is named in `.oxlintrc.json`'s override. The shared helpers in `src/test/testing.ts` for a Story that plays many frames: `playedThrough(model, messages)`, the Model the Messages leave with every sound, cue, and save write completed (`settleRunCommands`); `modelAfterMessages`, the same with no Command left pending; `eventsOver(start, messages)`, every event the frames raise; `startedRun(model)`, PLAY and START from home; `messageIfAny(choose)`, a sim's player acting on the Model it finds, sending nothing (a `SuppressedContextMenu`, which the root answers with nothing) when it has nothing to do (`src/input/__tests__/couch.sim.test.ts`, `src/features/bots/__tests__/teammateBot.sim.test.ts`); and `changeModel(change)`, a sim's own rule applied mid-Story as `Story.given` applies one at the start (hearts refilled, every zombie killed the frame it walks in). A helper that gathers every frame (`eventsOver`, `recordTicks`, a sim's arrivals) fills an array its own `Effect.suspend` makes, so each run starts empty, and hands it back from the Story's Effect. A sim stretch that runs past where its player would act differently (a wave that ends mid-stretch) is cut at that frame, and the next Story starts from the Model it left.
- **A new Model field joins `tools/determinism/fields.ts`**: a child's field is `Client`.

### Strictness

`typecheck` and `lint` are strict on purpose, so the easy way to write code is the right way. Every project extends `tsconfig.base.json`, the tools too: they are held to the game's rules.

- **`typecheck`** is strict TypeScript plus unused locals and parameters, `override`, no switch fallthrough, erasable syntax only, `import type` for types, and bracket access for index signatures (`process.env['X']`). Every Effect language service diagnostic is on, at error (see "Effect, all rules on" below). `typecheck` runs the Effect-patched `tsrs` (`effect-tsgo tsrs`).
- **`lint`** is oxlint's correctness and perf categories, type-aware rules (floating promises, exhaustive switches, no unsafe `any`, strict booleans), the Foldkit rules, and every Effect rule (`.oxlintrc.effect.json`: the strict preset plus each rule it leaves out). Both oxlint passes run their type-aware rules on the Effect-patched `tsrs` (`effect-tsgo --tsrs-lint oxlint`), not tsgolint. In `src` it also enforces the Rules above: no `Math.random`, `Date.now`, `crypto.randomUUID`, or `Data.taggedEnum`, no `.guards` outside tests, `performance.now` only in `subscriptions.ts`, storage only in the store, and no `VIEW_WIDTH` or `VIEW_HEIGHT` in overlays. In the tools and the packages it bans `Math.random`, `Date.now`, `Data.taggedEnum`, `setTimeout`, `setInterval`, and `fetch`. The project's own rules live in `tools/lint/munchPlugin.ts` (the rules about tests in `tools/lint/testRules.ts`, imported by full file name, since oxlint loads the plugin in Node), an oxlint JS plugin in TypeScript over `@oxlint/plugins`' typed AST, which the root and `infra` configs both load and `tools/lint/munchPlugin.test.ts` runs on code each rule must and must not flag: `munch/no-tag-chain`, `munch/no-extract-tag`, `munch/no-raw-json`, `munch/no-conditional-step`, `munch/no-world-spread`, `munch/no-menu-field`, `munch/command-beside-update`, `munch/no-run-in-tests`, `munch/no-floating-story`, `munch/no-plain-story`, `munch/live-test-note`, `munch/tap-by-click`, `munch/seat-action-once`, `munch/key-action-once`, `munch/no-binding-field-write`, `munch/folder-imports`, and `munch/disable-needs-reason` (see "Code shape" and "Blocks and Bindings"). A new rule gets its cases there. A disable comment that silences nothing fails lint (`--report-unused-disable-directives-severity=error`). No file anywhere has an em dash (`tools/lint/noEmDash.sh`), no file is over 1200 lines (`max-lines`, in the root and `infra` configs), every module in `src` has its row in the file tables above (`tools/lint/fileTable.ts`) and sits in its layer's folder, its tests in `__tests__/` (`tools/lint/folders.ts`), and no helper is copied between files (`tools/lint/duplicateHelpers.ts`, see "Code shape"), and nothing is dead: `knip` (`knip.jsonc`) fails an unused file, export, type, or dependency in `src`, the packages, `infra`, and the tools.
- **The tools follow the same rules**, and so do the build and test configs (`vite.config.ts`, `vitest.config.ts`, the harness's), linted with the tools and typechecked in `tools/vite`. No `any`, no `as`, no `!`, strict booleans, JSON through Schema (`tools/json.ts`: `readJsonFile` and `writeJsonFile` as Effects over `FileSystem`, `decodeJson`, `encodeJson`), and Effect's clock, timers, `HttpClient`, `Schedule`, `Console`, `Config`, `FileSystem`, `Path`, and `ChildProcess` in place of `Date`, `setTimeout`, `fetch`, polling loops, `console`, `process.env`, and `node:fs`, `node:path`, and `node:child_process`. A script is an Effect program from end to end. An audit reads the page through the typed globals in `tools/audit/page.ts` (`window.__model` is the game's `Model` inside `page.evaluate`) and brings a value back out with `evaluateAs(page, schema, fn)` or `modelAs(page, schema)`, a Schema of only the fields it reads. A timing audit reads the wall clock with `nowMs()` from `tools/audit/lib.ts` (Effect's `Clock`) and polls with `pollUntil` (a `Schedule`). The only disables left are in code that runs inside the page, where Effect is not loaded (its own timers, `fetch`, `requestAnimationFrame`, async functions, and native array and string methods), each with its `NOTE:`.
- **Never silence a rule without a one-line reason**: a `// NOTE:` just above the `oxlint-disable-next-line` or `@effect-diagnostics-next-line` comment (within six lines), `-- why` after the rule, or a comment on the override in the config. `munch/disable-needs-reason` fails a silencer with neither, and lint fails one that silences nothing.
- **Effect, all rules on.** Every `@effect/language-service` diagnostic is at error in `tsconfig.base.json`, and every Effect oxlint rule in `.oxlintrc.effect.json` (and infra's), with none turned off. Where they disagree with `FOLDKIT.md`, they win: a Command's fallback Message is `Effect.orElseSucceed(...)`, not `Effect.catch(() => Effect.succeed(...))`. What they ask of code:
  - An exported function of two or more fixed arguments is dual: a data-first and a data-last call signature, built with `Function.dual(arity, impl)` (`missingPipeableSignature`). When an optional argument makes the count ambiguous, tell the two forms apart with a cheap test from `src/shared/dualArgs.ts`, or make the argument required. Pass a dual function to a callback through a lambda, never point-free: `Array.map` passes an index too.
  - Native array, string, and `Object` methods go through effect's `Array`, `String`, and `Record`, imported under those names from `effect` (the global is then `globalThis.String`). `findFirst`, `indexOf`, `charAt`, and the like return an `Option`.
  - A number in a Schema is `Schema.Finite`, not `Schema.Number`.
  - An error is a `Schema.TaggedError` class built with `.make`; `Effect.try` and `tryPromise` have a `catch`; Schema decodes through its Effect, Option, or Result forms, not `decodeSync`; a Layer is built in the program's scope, not `Effect.provide`d along the way; and no `yield*` sits in a call's arguments.
  - An unstable Effect API is allowed by its module in `allowedUnstableApis` in `tsconfig.base.json`. Our own export that hands out an unstable type (`SqlClient`, `FileSystem`, a sync-engine `Mutation`) is marked `@stability unstable`, and its module joins that list. Better still, keep the type out of the export, as `src/platform/lobbyWrite.ts` keeps `Mutation` out of `RoomAccess`.
  - The only Effect disables are where Effect cannot be used: the service worker (`src/platform/sw/worker.ts`, which loads no modules, with its overrides in both configs), code that runs inside an audit's or a video's page, and the two Foldkit views (`view` in `src/app/view.ts` and `src/features/coop/view.ts`: Foldkit knows a view by the function `makeView` returns, so it cannot be wrapped in a dual).

### Code shape

- **Match every union exhaustively**, with the Schema union's `.match` or `Match.valueTags`, not an if/else chain on `_tag` that ends in a catch-all. When only some variants matter, say so: the union's `.matchOrElse`, or `Match.value(x).pipe(Match.tag(...), Match.orElse(...))` for a union with no Schema, such as `Canvas.Shape` or Effect's `SchemaAST`. `munch/no-tag-chain` fails two or more `_tag` checks on one value in a row (or on a tag held in a variable named `tag` or `...Tag`): `else if`, early returns, or nested ternaries. A lookup by tag is a record typed over the union's tags (`{ readonly [Tag in ServerFrame['_tag']]: ... }`), so a new variant fails typecheck until it has its entry. One check alone is fine. In per-frame code, keep a single check or `isAnyOf` cheap: build no handler object per entity per frame.
- **Keep the client out of the World's types.** A module the co-op room reaches (`stepWorld.ts`, `roomWorld.ts`, and what they import) imports a World type from where it is declared (`worldSchema.ts`, `entitySchema.ts`, `wireNumber.ts`), never through `model.ts`, and never takes the client `Model`, not even by `import type`. A rule that reads only World fields takes a `World`, or `<M extends World>(model: M): M` built with `modifyWorldFields` (`src/world/schema/world.ts`) so single player gets its own Model back; one that reads a client field lives in a client module (`frame.ts`, `home.ts`, `src/app/update/`). Such a module lives in `src/world/` or `src/shared/`, and `munch/folder-imports` and `bun run world:check` keep the client out of it ("Folders").
- **A player's state lives in `seats`, and a per-player rule takes a slot.** The World holds one `SeatState` per player (the seat's record, `player`, `intent`, `boosts`, `trapStock`, `selectedTrap`, `laserSight`, `purchase`, `cooking`, `feats`) in slot order, single player's at `SOLO_SLOT`. A rule that acts for one player is `(world, slot, ...)`: it reads with `seatStateAt(world, slot)` and writes with `modifySeat(world, slot, {...})`, or `seats: atSeat(slot, {...})` among other World fields in one `modifyFields`. `forEachSeat(world, (current, slot) => ...)` goes in seat order and never rebuilds the World to put a seat in place. A screen reads the seat it is about with `focusOf(model)` (the first seat: the only one in single player, a co-op client's own after `focusSeat`) and writes it with `modifyFocus`; a rule that is about no one seat (the wave, the boss's room) reads no seat. A seat added to the World joins `SeatState` in `src/world/schema/worldSchema.ts`, which is a protocol change (`packages/netcode/src/Protocol.ts`).
- **Merge a World result with `withWorld`**, never `{ ...model, ...world }`. `munch/no-world-spread` fails a value named as a World (`world`, `nextWorld`, `x.world`) spread after the first spread.
- **Ask `menuState(model)` which menu is up** (`src/app/menuState.ts`). It derives a `MenuState` from the dialogs, the lobby, co-op, and the phase, top first (Profile, Panel, Hand, InstallSteps, UpdateGreeting, HeroPicker, Lobby, Coop, then Home, Playing, Paused, or EndScreen; the lobby's own reads are `isLobbyShown` and `isHeroPickerUp` from `src/features/lobby/model.ts`), and is never stored. Update's gates and the view read it or its helpers (`isOnHomeMenu`, `isPanelOpen`, `isProfileOpen`, `isProfileOpenOn`, `isHandOpen`), so they agree. `munch/no-menu-field` fails a dialog's `.isOpen` and `model.coop.screen` anywhere else in `src` but tests (co-op's own routing reads `isCoopOpen`). A new root dialog joins `MenuState` and the rule's list together.
- **Define a Command beside the update that returns it**, as FOLDKIT.md asks, not in a module of Commands: the Step that returns `WriteSave` and `WriteSave` both live in `update/save.ts`. Only the Commands init starts live apart, in `boot.ts`, which returns them as `bootCommands`. Every root Command's `.layer` joins `CommandsLayer` in `layer.ts`. `munch/command-beside-update` fails a `makeCommand` whose module never calls it.
- **Run a Step on a condition with `stepWhen(isDue, step)`** (`src/shared/stepWhen.ts`, generic, so co-op's update uses it too), and build a Step that only changes the Model with `modelStep(change)` (`src/app/update/step.ts`). `munch/no-conditional-step` fails `cond ? step(m) : { model: m }` (or `unchanged(m)`) either way round. When the condition narrows a union, match it (`Screen.matchOrElse`). Inside `makeStep`, pick between Steps with `cond ? step : unchanged`. Name a Step for what it does, with no `Step` suffix.
- **A player action's rule lives once, in stepWorld; single player calls it through withWorld.** Swapping, the knife, drawing a gun, reloading, traps, READY, and MEDIC! are `SeatAction`s, each decided once in `src/world/step/stepWorld.ts` (`trySeatAction`, `applySeatAction`), where the co-op room runs them too. Single player's handler applies one to its lead seat with `actAsLead` or `tryAsLead` (`src/app/update/action.ts`, over `withWorld`), keeps its client checks in front (the menus, the new zombie card), and wraps only its cues around it (sounds, `dropClip`, focus), read from the result or the refusal. Buying in the world (hold or stand to buy, with keys off the crew's ring: the boards, the fridge, a case's prize) rides in the intent and lives in the tick. `src/app/update/__tests__/seatAction.parity.test.ts` runs every action both ways from the same World, keyed by the union's tags, so a new action needs its row; `munch/seat-action-once` fails a rule's own steps (`swapInHand`, `beginReload`, `startWaveEarly`, ...) imported, or a seat's fields (`player`, `traps`, `trapStock`, `selectedTrap`) written with `modifyFields`, `modifyFocus`, `modifySeat`, or `atSeat`, in `src/app/update/`, `main.ts`, `runFlow.ts`, and `couch.ts`.
- **A key presses a seat action through one table**, `src/input/keyActions.ts`: `playerKeyAction(model, code)` for single player and co-op's client, `keyActionOf(seat, keys, code)` for a couch player's own keys. It also keeps READY's key, the interact key, from starting a wave at a purchasable, where it is held to buy. `munch/key-action-once` fails any other module that imports `isInteractTaken` to decide a key itself.
- **An online run's Messages go through `orInRun`** (`src/app/update/coopRun.ts`): the handler wraps its single player Step, `makeStep(orInRun(message, swapFromButton))`, and `orInRun` checks `isRunOn` once and matches the Message. A new Message a co-op run handles its own way joins `RunMessage` there.
- **Read and write JSON through Schema** (`Schema.fromJsonString(schema)`, or `HttpClientRequest.schemaBodyJson` and `HttpClientResponse.schemaBodyJson` over HTTP), not `JSON.parse` or `JSON.stringify`. `munch/no-raw-json` fails them in `src`, the packages, and `infra`; the few files allowed are overrides in the configs, each with its reason.
- **Pack a World number on the co-op wire by its Schema.** A number with no `wire` annotation goes exactly. A lossy packing is named on the Schema (`PositionNumber`, `VelocityNumber`, `UnitNumber`, `MillisNumber`, and the `Point`, `Heading`, and `Push` vectors in `src/world/schema/wireNumber.ts`), never picked by field name. `src/world/net/__tests__/worldCodec.test.ts` lists every lossy number and pins the bytes of a scripted room: a change to either is a protocol change.
- **Describe a thrown value with `describeError`** (`src/shared/describeError.ts`), not a copy of `error instanceof Error ? error.message : String(error)`.
- **Retry and back off with a `Schedule`**, not a loop or a timer.
- **Name a variant once**: `type Turret = typeof Trap.Turret.Type` beside the union (`typeof Union.cases.Name.Type` for an Effect `Schema.TaggedUnion`, an `interface` member for a plain union), not `Extract<Trap, { _tag: 'Turret' }>` at each use. `munch/no-extract-tag` fails the `Extract` form.
- **Share helpers, never copy them.** Canvas shape helpers (`rect`, `pixelArt`, `centeredRect`) live in `src/render/drawing.ts`, HTML parts the menus and overlays share (`iconView`, `keyCapView`, `percentOf`) in `src/ui/menuParts.ts`, vector and timer helpers (`distanceBetween`, `OUTWARD`, `countDown`) in `src/world/step/geometry.ts`, and anything else in the module it is about (phase checks such as `isEndScreen` in `src/domain/run.ts`), exported from there. `tools/lint/duplicateHelpers.ts` (in `bun run lint`) fails a top-level function, or a constant built from an object, array, or call, that two modules of one code base (`src` and the tools, a package's `src`, infra's Worker) declare with the same body, where every name the body reads means the same thing. A copy under a new name fails too (`NO_PUSH` beside `ZERO_VECTOR`), so before writing a helper, find the one that already holds that value and import it. A script's own state (what it awaits, an empty list it fills, what it reads from its arguments, environment, clock, or `import.meta`) is never a copy. Its `ALLOWED` list holds the few copies left on purpose, each with a reason, and fails an entry that no longer matches.
- **Share test setup, never copy it.** Steps, locators, and builders of zombies, bullets, and guns live in `src/test/testing.ts`; the named Models a test starts from (`home`, `readyModel`, `quietWave(wave)`, `atFridge(keys)`, `withKeys(model, keys)`), the changes tests make to one, and spawns live in `src/test/model.fixture.ts`; a package's in `test/fixtures.ts`, the Worker's in `infra/worker/testing.ts`. Group a Story setup of several steps with `Story.steps(...)` and pass it whole (`tap(code)`, `finishSplash`), not as an array to spread. Keep the steps a test is about in the test itself: a fixture holds the state it starts from, never the behavior under test. `tools/lint/duplicateHelpers.ts` checks test files the same way, against each other and the shared homes, and fails a name two shared homes both export (`readyModel` meant two Models once): a different value gets a name that says which (`shopReady` and `SHOP_FRAME_MS`, before the shop went).
- **Effect tests use `it.effect` from `@effect/vitest`.** It runs the test's Effect with a Scope and the TestClock, so time moves only when the test moves it (`TestClock.adjust`, or `settle` and `first` from `@munch/sync-engine/testing` to wait for an event). Use `it.live` only where a test needs real time (a real timer, a real worker, real document events), with a `NOTE:` right above it saying why (`munch/live-test-note`); a network that sleeps runs on the TestClock with `settle`, as sync-engine's engine tests do, and `layer(...)` to share a Layer across a file's tests. A failure to check is `Effect.exit` inside the test. `munch/no-run-in-tests` fails `runPromise`, `runPromiseExit`, `runSync`, `runSyncExit`, `runFork`, and `runCallback` off `Effect`, a `Runtime`, or a runtime of the test's own (`ManagedRuntime.make` too) in test files and their shared setup. Story and Scene tests are Block-aware `Story.story` and `Scene.scene` under `it.effect` ("Tests drive the root through Block-aware Stories and Scenes"). The Worker's tests run the same way, under Bun (`bun --bun vitest run`), with infra's own `@effect/vitest`.
- **Export only what another module reads, and delete what nothing reads.** `knip` in `bun run lint` fails an unused file, export, exported type, or dependency. An export a module only uses itself loses its `export`. A new entry (a script run with `bun`, a worker, a config) joins its workspace's `entry` list in `knip.jsonc`, and a file another change is editing may sit in `ignoreIssues` with a `TODO`, never for good. Every name a player reads, run modes too, lives in `src/world/names.ts`.
- **No import cycles.** `import/no-cycle` fails a module that imports one that imports it back, type imports too, in the root and `infra` configs. Break one by moving what both need into a module about it (`onlineRun.ts` holds the reads of an online run that the update modules and the drawing share; `bindings.ts` the Bindings that Steps and folds share).
- **A file past 1200 lines holds two jobs**: split it along its section headers into modules with one job each, moving code as it is and adding no barrel. `max-lines` fails it, in `.oxlintrc.json` and infra's config, with no exceptions. State a file's sections share goes in one record passed to them (the balance bot's `BotState`, the audit harness's `HarnessPage`), since an import cannot assign another module's `let`. A split test file's shared setup goes in a `*.fixture.ts` in its `__tests__/` (`boss.fixture.ts`), checked as a test home by `tools/lint/duplicateHelpers.ts`. A new module in `src` goes in its layer's folder ("Folders") and gets its row in that folder's file table above: `tools/lint/fileTable.ts` fails a module or stylesheet no table names, and a row naming a file that is gone.

### Git

- Use Conventional Commits, such as `feat: add the shop` or `fix: stop the stick sticking on cancel`.
- Give a commit a body that says what was wrong or missing and what changed.
- Do not add `Co-Authored-By` lines or any AI attribution to a commit message.
- Do not commit or push unless asked.

### Changelog

`CHANGELOG.md` is for players, not developers. Keep it fun and short so it never feels spammy.

- One entry per day that shipped something a player would notice, newest first, headed `## <Month D, YYYY>: <short fun title>`. Add to today's entry instead of starting a second one.
- At most about five bullets a day, each one line with one emoji, saying what changed for the player. Skip refactors, tests, tooling, and anything invisible.
- Goofy and plain, like the game's own copy. No version numbers, commit hashes, or file names.
- When a change ships something players will notice, add or update today's bullet in the same push.

### Waiting on the owner

`TANNER_TODO.md` lists what is blocked on the owner: accounts to set up, decisions, and reviews. When work stops on the owner, add an item there with the exact steps. Remove it once it is done.

### Prose

Do not use em dashes in documentation, comments, or commit messages. Use a period, a comma, or a colon.
