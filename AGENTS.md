## Project Notes

A pixel-art zombie shooter, live at https://munchmanor.com (the old `workers.dev` address keeps serving the same build: see "Two origins" in `PLATFORM.md`). It runs on desktop and on phones. The vision, the decided choices, and the roadmap are in [`GAME_DESIGN.md`](./GAME_DESIGN.md): read its "Decided" section before changing how the game plays. Co-op is planned in [`MULTIPLAYER.md`](./MULTIPLAYER.md). The Cloudflare side (hosting, analytics, the on-device SQLite save, and sync) is in [`PLATFORM.md`](./PLATFORM.md).

Before you finish a change, run `typecheck`, `lint`, `test`, and `build`. All four must pass. Also run `test:full` when the change touches gameplay (`simulation.ts`, `waves.ts`, `pacing.ts`, `combat.ts`, the zombie, boss, or trap modules), since CI runs it and blocks the deploy on it.

**Go easy on the laptop.** One 12-core laptop often runs several agents at once. Two agents running 8-process balance batches together pushed the load average to 30 and made every step about three times slower.

- Run every heavy job through the guard: `bun run balance`, `bun run perf:check`, or `bun run heavy -- <command...>` for anything else heavy, such as an audit or a shots script. Never call `tools/balance/simulate.ts` or a heavy audit directly.
- The guard aims at about 70% of the machine: a 1 minute load near 0.70 x cores (8.4 on 12, `HEAVY_TARGET_LOAD` to change it). A job starts only when the load, the jobs started in the last minute, and its own cost fit under that target.
- **Timing** jobs (`perf:check` and the timing audits, `splash.ts`, and any command it does not know) run alone. **CPU** jobs (the balance bot, nightly, wave snapshots, determinism) run one at a time beside audits and size their `WORKERS` to the budget, up to 8. **Shared** jobs (the shots scripts, `taps.ts`, and the other screenshot and functional audits) run up to 4 at once, each costing about one core per browser context. `--timing`, `--cpu`, or `--shared` before the command overrides the class.
- **Long jobs yield.** The balance bot plays its runs in chunks of about 25 (a wave pass by snapshot slot), the nightly yields between its jobs, `splash.ts` between profiles, and `perf:check` between scenarios. At each boundary the guard hands over to any waiting job and queues again, so nobody waits long behind one batch. Results are the same as one unchunked run. A new long script should do the same with `yieldTurn` from `tools/heavy/turn.ts`.
- **The queue goes round by worktree.** A worktree that just had a turn goes behind other worktrees' waiting jobs; otherwise jobs go by arrival. A Shared job may start ahead of a Timing or CPU job that only waits for a running CPU job (backfill).
- **A solo turn is a 10 minute lease** (`HEAVY_LEASE_MINUTES`). A job past it keeps running, but the guard says so loudly and waiting jobs name it: split such a job so it yields.
- `bun run test` sizes vitest's workers to what is left of the budget (at least 2) and counts itself, so test runs from several agents share the target. CI is unaffected.
- The guard refuses a sixth balance batch per branch without `--allow-more` (`bun run heavy -- --reset-budget` starts the count again). How it works is in [`tools/heavy/README.md`](./tools/heavy/README.md).
- Cap tuning at about three batches per change. Use 100 runs to sort ideas and 200 only to confirm the final numbers. Results within a few points of a target are fine: list misses as follow-ups instead of running more batches.

**Check balance in tiers**, cheapest first, as "How balance is checked" in `GAME_DESIGN.md` describes: `bun run test` (the model's guardrails) on every change, `bun run test:full` (also the wave 2 snapshot smoke pass), `bun run balance -- --wave N --runs 100` while tuning a wave, and `bun run balance:nightly` once a change is done. A guardrail not met yet is a `test.todo` in `tools/balance/model.test.ts`; flip it to `Met` once a change brings it in. Rewrite `tools/balance/baseline.json` (`bun run balance:nightly -- --update-baseline`) only in a change that means to move the numbers, and say so in the commit body.

### Rules

- **Keep the game deterministic.** `update` is pure. It never calls `Math.random` and never reads the clock. Randomness comes from the seeded generator whose state lives in the Model, so the same seed and the same Messages give the same game.
- **Support desktop and touch.** Every input must work with a keyboard and mouse and with touch. Touch tracks each finger by its `pointerId`, so two thumbs work at once.
- **Buttons act on OnClick.** `src/touchTaps.ts`, mounted on the game's root, turns each finger's tap into a click from its own pointer events, so a button works with another finger on the glass and acts once. Never act on a touch or mouse release (`munch/tap-by-click`); `OnPointerDown` is for acting the moment a finger lands. An animation never moves a button or what holds one: it fades or flashes in place, and only art inside moves (`src/motion.test.ts`).
- **Support portrait and landscape on phones.** A touch phone held upright plays in the portrait layout (see "Portrait play" in `GAME_DESIGN.md`). Overlay code reads the screen from `screenOf(model)`, never `VIEW_WIDTH` and `VIEW_HEIGHT`, and CSS reads `--screen-w`, `--screen-h`, `--world-top`, and `--frame-top` (the top of the banners' frame) from `.game-root`, with `[data-layout='Portrait']` rules for portrait. Check a layout change with `tools/audit/shots34.ts` and `PORTRAIT=1 bun taps.ts`. The installed Android app starts in landscape and turns only when Settings' ROTATE is on (see "Rotation" in `GAME_DESIGN.md`).
- **Follow the design doc.** Choices under "Decided" in `GAME_DESIGN.md` are settled. The "Reference notes" are ideas, not decisions. If a change goes against a decision, say so before making it.
- **Show, don't explain.** Fewer words, more visuals. Prefer icons, art, motion, and sound to text, keep every label and line short, and never repeat what a player has already seen. Write new copy that way, and trim old copy you touch. See "Show, don't explain" in `GAME_DESIGN.md`.
- **Use original art and names.** Do not copy art, names, or item lists from Zombie Estate 2.
- **Use Effect fully.** Reach for Effect's own APIs (Schema, Match, services, resources, `effect/sql`) rather than working around them. Keep the `@effect/language-service` plugin in `tsconfig.base.json`: without it `typecheck` still passes but reports no Effect problems.
- **Draw fixed art as sprite images.** A pixel map goes through `spriteShapes`, and a fixed list of whole pixel rectangles goes through `bakeShapes`. Build them once at module scope or in a cache, never per frame. A production build packs every sprite into a prebuilt atlas (`tools/sprites/`, see `docs/IMAGES_PLAN.md`), found by content key, so the game draws cropped regions of a few PNG files instead of encoding one per sprite. A sprite built lazily, on first use, must be listed in `src/spritePrecompile.ts`, or `tools/sprites/atlas.test.ts` fails. HTML that shows a sprite as an `<img>` takes `standaloneSource(image)`, since an `<img>` cannot crop. Tests draw stand-ins instead of PNGs (`src/vitest-setup.ts`). Shapes that change every frame, such as particles, bars, and decals, stay `Rect` shapes.
- **Read the map from the level.** The map is data: the Model's `level` names the level and its open exits, and `levelOf(model)` hands back the built `Level` with its tile lookups, doors, thresholds, and spawn doors. Every function that reads tiles, doors, or the level's size takes that `Level`. Only a fresh run (which starts in the parlour) and the stall (which stands there) read `PARLOUR` directly. Caches of anything derived from the map key on the `Level` (a new record whenever an exit opens), as the flow field, the pathing tables, and the room canvas do.
- **Keep the frame cheap.** `src/perf.scene.test.ts` budgets the canvas shapes and paint operations of a full room, and `bun run perf:check` gates frame time against a recorded baseline (see `tools/audit/README.md`). In code that runs every frame, check a union's tag with `isAnyOf`, not `guards`: a guard validates the whole value through Schema, and `Phase` carries the wave's spawn list.
- **Persistent data goes through the store.** Anything that must last across reloads goes in `PlayerSave` (its Schemas in `src/playerData.ts`, the rest in `src/save.ts`), with a bump of `SAVE_VERSION` and a migration or a fallback to no save for the older version. Add it to `saveOf` and `restoreSave`. `update` then writes it on change through the `WriteSave` Command, which goes through `PlayerStore` in `src/store.ts`. Never touch SQLite, OPFS, or `localStorage` anywhere else. Other SQLite code goes through `@munch/sqlite-wasm-effect` (see its README).
- **Player data changes go through sync mutations.** The save lives in the player sync scope (`src/playerScope.ts`): a change to it is a mutation, never a direct write to the `player` or `kills_by_kind` tables. A new kind of change gets a `PlayerChange` case and its place in `changesBetween` (`src/playerSync.ts`), a mutation in `src/playerScope.ts` with a deterministic apply (time only from its context, no randomness, increments rather than totals where two devices can both change it), and its case in `runChange` in `src/storeSqlite.ts`. A new column or table is a new numbered scope migration; never edit one that has shipped, and bump a mutation's `version` when its args change. The same file runs in the sync Worker, so keep it to `effect`, the engine, and `src/playerData.ts`. See "What phase 4 built" in `PLATFORM.md` and `packages/sync-engine/README.md`.
- **Send analytics only through SendRunSummary.** The summary is built in `update` from the Model (`src/analyticsRun.ts`), the network call lives in the Command, and nothing is sent when "Share anonymous play stats" is off. A new field goes in `RunSummary` in `src/analytics.ts` with a bump of `RUN_SUMMARY_VERSION`, and a new D1 migration in `infra/migrations`. Nothing personal goes in a summary.
- **Write tests for game logic** as Story tests that replay Messages. Break the code once to see the test fail before you trust it.
- **Keep `bun run test` fast.** A test that plays more than about one wave of game time, or takes more than 300 ms, goes in a `*.sim.test.ts` file beside its Story test, which only `test:full` and CI run. A file that needs a page (it builds elements, dispatches window events, or uses `localStorage`) starts with `// @vitest-environment happy-dom`; the rest run in plain Node, and Scene tests always get a page. Files share a worker's modules (`isolate: false`), so a test that changes a global (a spy, a stub, `localStorage`) puts it back in `afterEach`. The nightly workflow runs `test:full` in a shuffled order to catch one that does not. See `vitest.config.ts` and `docs/TESTING_PLAN.md`.

### Blocks and Bindings

The root and its children are Foldkit Blocks (see `FOLDKIT.md`, and `repos/foldkit/examples/pixel-art` for a canvas game with dialogs).

- **The root is split by role.** `definition.ts` holds `ApplicationDefinition` and its helpers, `bindings.ts` the Bindings, `composition.ts` their OutMessage folds and `ApplicationComposition` (a fold calls Steps and a Step calls a Binding, so the Bindings sit apart, as FOLDKIT.md's "OutMessage policies" lays out), `main.ts` init and the handler record, `view.ts` the view, `block.ts` the assembly, `layer.ts` the root's handler Layer, and `services.ts` `ApplicationLayer`. `entry.ts` only starts the Program.
- **A child lives on a Model field through its Binding.** Each dialog, tab strip, the Look tab, and co-op is a Binding on the field of the same name, so its Messages arrive as `Got<Field>Message` (`GotShopDialogMessage`). Its state starts in `initialModel`, so the Binding says `init: false`. Never write a child's field from the root: ask through its operations (`ShopDialogBinding.requestOpen()`, `CoopBinding.requestPressKey({ code })`, `CoopBinding.requestKeepTracers(...)`) and answer its OutMessages in the Binding's fold. `munch/no-binding-field-write` fails a `modifyFields` that writes a Binding's field in `src` outside tests; a new Binding joins its list. A child Block gets only its own fields; it learns about the root through operations and view inputs.
- **Two kinds of Step.** A plain `UpdateStep` changes only the root and returns root Commands. A Step that calls a Binding operation is built with `makeStep(model => ...)` and returns a deferred Step, usually `Update.combineSteps([...])`; only a handler's own Model (or `makeStep`'s) may run it, never a Model built with `modifyFields` along the way. Use `combine` from `update/step.ts` for plain Steps.
- **Every change settles once.** The after-message Steps (`afterMessage` in `update/settle.ts`: music, end focus, rotation, Nightmare, the run count and summary, the save) end every handler: `settle(model, result)` for a plain result, `Update.combineSteps(model, [step, ...afterMessage(model)])` for a connected one. A child Message that changes only its own field needs none of them, as they read only the root's fields, so they also end every OutMessage fold (`settled`). A fold that a handler's operation sets off settles again inside it; that is safe while folds change nothing those Steps read, so keep it that way.
- **Commands and Subscriptions carry handlers.** A Command is `makeCommand(name, { args, messages, handler: function* () { return args => effect } })`, defined beside the update that returns it, and its `.layer` joins `CommandsLayer` in `layer.ts` (`AppHandlers` is read off it). A Subscription is a named entry in `makeSubscriptions` with the Messages it may emit. Co-op's own go through `CoopDefinition` and co-op's `CommandsLayer`.
- **Tests drive the root's update and view.** Scenes run `scene(ROOT, ...)` and emit through `SCENE_SUBSCRIPTIONS.<entry>` (both in `src/testing.ts`). A child's Message is `toParentMessage(Binding, childMessage)` from `foldkit/test`; a Dialog's Commands are `Dialog.test.ShowDialog` and `Dialog.test.CloseDialog`, resolved with `DialogBlock.Message`. A Message no Subscription emits is a Command's or Mount's result: resolve that, or start the scene from `update(model, message).model`.
- **A new Model field joins `tools/determinism/fields.ts`**: a child's field is `Client`.

### Strictness

`typecheck` and `lint` are strict on purpose, so the easy way to write code is the right way. Every project extends `tsconfig.base.json`, the tools too: they are held to the game's rules.

- **`typecheck`** is strict TypeScript plus unused locals and parameters, `override`, no switch fallthrough, erasable syntax only, `import type` for types, and bracket access for index signatures (`process.env['X']`). The Effect language service runs at error, suggestions included: no global `Math.random`, `Date`, timers, `fetch`, or `crypto.randomUUID`, JSON through Schema, Schema classes built with `make`, and deterministic service keys.
- **`lint`** is oxlint's correctness and perf categories, type-aware rules (floating promises, exhaustive switches, no unsafe `any`, strict booleans), the Foldkit rules, and the Effect strict preset. In `src` it also enforces the Rules above: no `Math.random`, `Date.now`, `crypto.randomUUID`, or `Data.taggedEnum`, no `.guards` outside tests, `performance.now` only in `subscriptions.ts`, storage only in the store, and no `VIEW_WIDTH` or `VIEW_HEIGHT` in overlays. In the tools and the packages it bans `Math.random`, `Date.now`, `Data.taggedEnum`, `setTimeout`, `setInterval`, and `fetch`. The project's own rules live in `tools/lint/munchPlugin.ts`, an oxlint JS plugin in TypeScript over `@oxlint/plugins`' typed AST, which the root and `infra` configs both load and `tools/lint/munchPlugin.test.ts` runs on code each rule must and must not flag: `munch/no-tag-chain`, `munch/no-extract-tag`, `munch/no-raw-json`, `munch/no-conditional-step`, `munch/no-world-spread`, `munch/no-menu-field`, `munch/command-beside-update`, `munch/no-run-in-tests`, `munch/live-test-note`, `munch/tap-by-click`, `munch/seat-action-once`, `munch/key-action-once`, `munch/no-binding-field-write`, and `munch/disable-needs-reason` (see "Code shape" and "Blocks and Bindings"). A new rule gets its cases there. A disable comment that silences nothing fails lint (`--report-unused-disable-directives-severity=error`). No file anywhere has an em dash (`tools/lint/noEmDash.sh`), no file is over 1200 lines (`max-lines`, in the root and `infra` configs), every module in `src` has its row in the file table above (`tools/lint/fileTable.ts`), and no helper is copied between files (`tools/lint/duplicateHelpers.ts`, see "Code shape"), and nothing is dead: `knip` (`knip.jsonc`) fails an unused file, export, type, or dependency in `src`, the packages, `infra`, and the tools.
- **The tools follow the same rules**, and so do the build and test configs (`vite.config.ts`, `vitest.config.ts`, the harness's), linted with the tools and typechecked in `tools/vite`. No `any`, no `as`, no `!`, strict booleans, JSON through Schema (`tools/json.ts`: `readJsonFile`, `writeJsonFile`, `decodeJson`, `encodeJson`), and Effect's clock, timers, `HttpClient`, and `Schedule` in place of `Date`, `setTimeout`, `fetch`, and polling loops. An audit reads the page through the typed globals in `tools/audit/page.ts` (`window.__model` is the game's `Model` inside `page.evaluate`) and brings a value back out with `evaluateAs(page, schema, fn)` or `modelAs(page, schema)`, a Schema of only the fields it reads. A timing audit reads the wall clock with `nowMs()` from `tools/audit/lib.ts` (Effect's `Clock`) and polls with `pollUntil` (a `Schedule`). The only disables left are in code that runs inside the page (its own timers, `fetch`, and `requestAnimationFrame`), each with its `NOTE:`.
- **Never silence a rule without a one-line reason**: a `// NOTE:` just above the `oxlint-disable-next-line` or `@effect-diagnostics-next-line` comment (within six lines), `-- why` after the rule, or a comment on the override in the config. `munch/disable-needs-reason` fails a silencer with neither, and lint fails one that silences nothing.

### Code shape

- **Match every union exhaustively**, with the Schema union's `.match` or `Match.valueTags`, not an if/else chain on `_tag` that ends in a catch-all. When only some variants matter, say so: the union's `.matchOrElse`, or `Match.value(x).pipe(Match.tag(...), Match.orElse(...))` for a union with no Schema, such as `Canvas.Shape` or Effect's `SchemaAST`. `munch/no-tag-chain` fails two or more `_tag` checks on one value in a row (or on a tag held in a variable named `tag` or `...Tag`): `else if`, early returns, or nested ternaries. A lookup by tag is a record typed over the union's tags (`{ readonly [Tag in ServerFrame['_tag']]: ... }`), so a new variant fails typecheck until it has its entry. One check alone is fine. In per-frame code, keep a single check or `isAnyOf` cheap: build no handler object per entity per frame.
- **Keep the client out of the World's types.** A module the co-op room reaches (`stepWorld.ts`, `roomWorld.ts`, and what they import) imports a World type from where it is declared (`worldSchema.ts`, `entitySchema.ts`, `wireNumber.ts`), never through `model.ts`, and never takes the client `Model`, not even by `import type`. A rule that reads only World fields takes a `World`, or `<M extends World>(model: M): M` built with `modifyWorldFields` (`src/world.ts`) so single player gets its own Model back; one that reads a client field lives in a client module (`frame.ts`, `home.ts`, `src/update/`). `bun run world:check` fails a client module in the room's bundle and in the files infra's typecheck reads (`INFRA_OWN_MODULES` in `tools/determinism/worldCheck.ts` names the few infra may see).
- **Merge a World result with `withWorld`**, never `{ ...model, ...world }`. `munch/no-world-spread` fails a value named as a World (`world`, `nextWorld`, `x.world`) spread after the first spread.
- **Ask `menuState(model)` which menu is up** (`src/menuState.ts`). It derives a `MenuState` from the dialogs, co-op, and the phase, top first (Shop, Profile, Panel, Hand, InstallSteps, UpdateGreeting, Coop, then Home, Playing, Paused, or EndScreen), and is never stored. Update's gates and the view read it or its helpers (`isOnHomeMenu`, `isPanelOpen`, `isProfileOpen`, `isProfileOpenOn`, `isHandOpen`, `isShopDialogOpen`), so they agree. `munch/no-menu-field` fails a dialog's `.isOpen` and `model.coop.screen` anywhere else in `src` but tests (co-op's own routing reads `isCoopOpen`). A new root dialog joins `MenuState` and the rule's list together.
- **Define a Command beside the update that returns it**, as FOLDKIT.md asks, not in a module of Commands: the Step that returns `WriteSave` and `WriteSave` both live in `update/save.ts`. Only the Commands init starts live apart, in `boot.ts`, which returns them as `bootCommands`. Every root Command's `.layer` joins `CommandsLayer` in `layer.ts`. `munch/command-beside-update` fails a `makeCommand` whose module never calls it.
- **Run a Step on a condition with `stepWhen(isDue, step)`** (`src/stepWhen.ts`, generic, so co-op's update uses it too), and build a Step that only changes the Model with `modelStep(change)` (`src/update/step.ts`). `munch/no-conditional-step` fails `cond ? step(m) : { model: m }` (or `unchanged(m)`) either way round. When the condition narrows a union, match it (`Screen.matchOrElse`). Inside `makeStep`, pick between Steps with `cond ? step : unchanged`. Name a Step for what it does, with no `Step` suffix.
- **A player action's rule lives once, in stepWorld; single player calls it through withWorld.** Swapping, the knife, drawing a gun, reloading, traps, buying, leaving the counter, and READY are `SeatAction`s, each decided once in `src/stepWorld.ts` (`trySeatAction`, `applySeatAction`), where the co-op room runs them too. Single player's handler applies one to its lead seat with `actAsLead` or `tryAsLead` (`src/update/action.ts`, over `withWorld`), keeps its client checks in front (the menus, the new zombie card), and wraps only its cues around it (sounds, chatter, `dropClip`, focus), read from the result or the refusal. Buying in the world (hold or stand to buy, the ammo window, the fridge) rides in the intent and lives in the tick. The shop dialog follows the World's shop through one `syncShopDialog` for both frame pipelines. `src/seatAction.parity.test.ts` runs every action both ways from the same World, keyed by the union's tags, so a new action needs its row; `munch/seat-action-once` fails a rule's own steps (`swapInHand`, `beginReload`, `purchase`, `startWaveEarly`, ...) imported, or a seat's fields (`player`, `wallet`, `traps`, `trapStock`, `selectedTrap`) written with `modifyFields`, in `src/update/`, `main.ts`, `runFlow.ts`, and `couch.ts`.
- **A key presses a seat action through one table**, `src/keyActions.ts`: `playerKeyAction(model, code)` for single player and co-op's client, `keyActionOf(seat, keys, code)` for a couch player's own keys. It also keeps READY's key, the interact key, from starting a wave at a purchasable, where it is held to buy. `munch/key-action-once` fails any other module that imports `isInteractTaken` to decide a key itself.
- **An online run's Messages go through `orInRun`** (`src/update/coopRun.ts`): the handler wraps its single player Step, `makeStep(orInRun(message, swapFromButton))`, and `orInRun` checks `isRunOn` once and matches the Message. A new Message a co-op run handles its own way joins `RunMessage` there.
- **Read and write JSON through Schema** (`Schema.fromJsonString(schema)`, or `HttpClientRequest.schemaBodyJson` and `HttpClientResponse.schemaBodyJson` over HTTP), not `JSON.parse` or `JSON.stringify`. `munch/no-raw-json` fails them in `src`, the packages, and `infra`; the few files allowed are overrides in the configs, each with its reason.
- **Pack a World number on the co-op wire by its Schema.** A number with no `wire` annotation goes exactly. A lossy packing is named on the Schema (`PositionNumber`, `VelocityNumber`, `UnitNumber`, `MillisNumber`, and the `Point`, `Heading`, and `Push` vectors in `src/wireNumber.ts`), never picked by field name. `src/worldCodec.test.ts` lists every lossy number and pins the bytes of a scripted room: a change to either is a protocol change.
- **Describe a thrown value with `describeError`** (`src/describeError.ts`), not a copy of `error instanceof Error ? error.message : String(error)`.
- **Retry and back off with a `Schedule`**, not a loop or a timer.
- **Name a variant once**: `type Turret = typeof Trap.Turret.Type` beside the union (`typeof Union.cases.Name.Type` for an Effect `Schema.TaggedUnion`, an `interface` member for a plain union), not `Extract<Trap, { _tag: 'Turret' }>` at each use. `munch/no-extract-tag` fails the `Extract` form.
- **Share helpers, never copy them.** Canvas shape helpers (`rect`, `pixelArt`, `centeredRect`) live in `src/drawing.ts`, HTML parts the menus and overlays share (`iconView`, `keyCapView`, `percentOf`) in `src/menuParts.ts`, vector and timer helpers (`distanceBetween`, `OUTWARD`, `countDown`) in `src/geometry.ts`, and anything else in the module it is about (phase checks such as `isEndScreen` in `src/home.ts`), exported from there. `tools/lint/duplicateHelpers.ts` (in `bun run lint`) fails a top-level function, or a constant built from an object, array, or call, that two modules of one code base (`src` and the tools, a package's `src`, infra's Worker) declare with the same body, where every name the body reads means the same thing. A copy under a new name fails too (`NO_PUSH` beside `ZERO_VECTOR`), so before writing a helper, find the one that already holds that value and import it. A script's own state (what it awaits, an empty list it fills, what it reads from its arguments, environment, clock, or `import.meta`) is never a copy. Its `ALLOWED` list holds the few copies left on purpose, each with a reason, and fails an entry that no longer matches.
- **Share test setup, never copy it.** Steps, locators, and builders of zombies, bullets, and guns live in `src/testing.ts`; the named Models a test starts from (`home`, `readyModel`, `quietWave(wave)`, `atFridge(balance)`), the changes tests make to one, and spawns live in `src/model.fixture.ts`; a package's in `test/fixtures.ts`, the Worker's in `infra/worker/testing.ts`. Group a Story setup of several steps with `steps()` from `foldkit/story` and pass it whole (`tap(code)`, `finishSplash`), not as an array to spread. Keep the steps a test is about in the test itself: a fixture holds the state it starts from, never the behavior under test. `tools/lint/duplicateHelpers.ts` checks test files the same way, against each other and the shared homes, and fails a name two shared homes both export (`readyModel` meant two Models once): a different value gets a name that says which (`shopReady`, `SHOP_FRAME_MS`).
- **Effect tests use `it.effect` from `@effect/vitest`.** It runs the test's Effect with a Scope and the TestClock, so time moves only when the test moves it (`TestClock.adjust`, or `settle` and `first` from `@munch/sync-engine/testing` to wait for an event). Use `it.live` only where a test needs real time (a real timer, a real worker, real document events), with a `NOTE:` right above it saying why (`munch/live-test-note`); a network that sleeps runs on the TestClock with `settle`, as sync-engine's engine tests do, and `layer(...)` to share a Layer across a file's tests. A failure to check is `Effect.exit` inside the test. `munch/no-run-in-tests` fails `runPromise`, `runPromiseExit`, `runSync`, `runSyncExit`, `runFork`, and `runCallback` off `Effect`, a `Runtime`, or a runtime of the test's own (`ManagedRuntime.make` too) in test files and their shared setup. Story and Scene tests stay Foldkit's `story` and `scene`. The Worker's tests run the same way, under Bun (`bun --bun vitest run`), with infra's own `@effect/vitest`.
- **Export only what another module reads, and delete what nothing reads.** `knip` in `bun run lint` fails an unused file, export, exported type, or dependency. An export a module only uses itself loses its `export`. A new entry (a script run with `bun`, a worker, a config) joins its workspace's `entry` list in `knip.jsonc`, and a file another change is editing may sit in `ignoreIssues` with a `TODO`, never for good. Every name a player reads, run modes too, lives in `src/names.ts`.
- **No import cycles.** `import/no-cycle` fails a module that imports one that imports it back, type imports too, in the root and `infra` configs. Break one by moving what both need into a module about it (`onlineRun.ts` holds the reads of an online run that the update modules and the drawing share; `bindings.ts` the Bindings that Steps and folds share).
- **A file past 1200 lines holds two jobs**: split it along its section headers into modules with one job each, moving code as it is and adding no barrel. `max-lines` fails it, in `.oxlintrc.json` and infra's config, with no exceptions. State a file's sections share goes in one record passed to them (the balance bot's `BotState`, the audit harness's `HarnessPage`), since an import cannot assign another module's `let`. A split test file's shared setup goes in a `*.fixture.ts` beside it (`boss.fixture.ts`), checked as a test home by `tools/lint/duplicateHelpers.ts`. A new module in `src` gets its row in the file table above: `tools/lint/fileTable.ts` fails a module or stylesheet the table does not name, and a row naming a file that is gone. A new art, audio, or client module joins `FORBIDDEN_GAME_MODULES` in `tools/determinism/worldCheck.ts`.

### Git

- Use Conventional Commits, such as `feat: add the shop` or `fix: stop the stick sticking on cancel`.
- Give a commit a body that says what was wrong or missing and what changed.
- Do not add `Co-Authored-By` lines or any AI attribution to a commit message.
- Do not commit or push unless asked.

### Changelog

`CHANGELOG.md` is for players, not developers. Keep it fun and short so it never feels spammy.

- One entry per day that shipped something a player would notice, newest first, headed `## <Month D, YYYY>: <short fun title>`. Add to today's entry instead of starting a second one.
- At most about five bullets a day, each one line with one emoji, saying what changed for the player. Skip refactors, tests, tooling, and anything invisible.
- Goofy and plain, like the game's own copy. No version numbers, commit hashes, or file names.
- When a change ships something players will notice, add or update today's bullet in the same push.

### Waiting on the owner

`TANNER_TODO.md` lists what is blocked on the owner: accounts to set up, decisions, and reviews. When work stops on the owner, add an item there with the exact steps. Remove it once it is done.

### Prose

Do not use em dashes in documentation, comments, or commit messages. Use a period, a comma, or a colon.
