Before you finish a change, run `lint` (which type checks too), `test`, and `build`. All three must pass. Also run `test:full` when the change touches gameplay (`simulation.ts`, `waves.ts`, `pacing.ts`, `combat.ts`, the zombie, boss, or trap modules), since CI runs it and blocks the deploy on it.

**Go easy on the laptop.** One 12-core laptop often runs several agents at once. Two agents running 8-process balance batches together pushed the load average to 30 and made every step about three times slower.

- Run every heavy job through the guard: `bun run balance`, `bun run perf:check`, or `bun run heavy -- <command...>` for anything else heavy, such as an audit or a shots script. Never call `tools/balance/simulate.ts` or a heavy audit directly.
- The guard aims at about 70% of the machine: a 1 minute load near 0.70 x cores (8.4 on 12, `HEAVY_TARGET_LOAD` to change it). A job starts only when the load, the jobs started in the last minute, and its own cost fit under that target.
- **Timing** jobs (`perf:check` and the timing audits, `splash.ts`, and any command it does not know) run alone. **CPU** jobs (the balance bot, nightly, wave snapshots, determinism) run one at a time beside audits and size their `WORKERS` to the budget, up to 8. **Shared** jobs (the shots scripts, `taps.ts`, and the other screenshot and functional audits) run up to 4 at once, each costing about one core per browser context. `--timing`, `--cpu`, or `--shared` before the command overrides the class.
- **Long jobs yield.** The balance bot plays its runs in chunks of about 25 (a wave pass by snapshot slot), the nightly yields between its jobs, `splash.ts` between profiles, and `perf:check` between scenarios. At each boundary the guard hands over to any waiting job and queues again, so nobody waits long behind one batch. Results are the same as one unchunked run. A new long script should do the same with `yieldTurn` from `tools/heavy/turn.ts`.
- **The queue goes round by worktree.** A worktree that just had a turn goes behind other worktrees' waiting jobs; otherwise jobs go by arrival. A Shared job may start ahead of a Timing or CPU job that only waits for a running CPU job (backfill).
- **A solo turn is a 10 minute lease** (`HEAVY_LEASE_MINUTES`). A job past it keeps running, but the guard says so loudly and waiting jobs name it: split such a job so it yields.
- `bun run test` sizes vitest's workers to what is left of the budget (at least 2) and counts itself, so test runs from several agents share the target. CI is unaffected.
- The guard refuses a sixth balance batch per branch without `--allow-more` (`bun run heavy -- --reset-budget` starts the count again). How it works is in [`tools/heavy/README.md`](./tools/heavy/README.md).
- Cap tuning at about three batches per change. Use 100 runs to sort ideas and 200 only to confirm the final numbers. Results within a few points of a target are fine: list misses as follow-ups instead of running more batches.

**Check balance in tiers**, cheapest first, as "How balance is checked" in `docs/GAME_DESIGN.md` describes: `bun run test` (the model's guardrails) on every change, `bun run test:full` (also the wave 2 snapshot smoke pass), `bun run balance -- --wave N --runs 100` while tuning a wave, and `bun run balance:nightly` once a change is done. A guardrail not met yet is a `test.todo` in `tools/balance/model.test.ts`; flip it to `Met` once a change brings it in. Rewrite `tools/balance/baseline.json` (`bun run balance:nightly -- --update-baseline`) only in a change that means to move the numbers, and say so in the commit body.

### Folders

`src/` is in folders by layer ("Where things are"). `tools/lint/folders.ts` (in `bun run lint`) fails a file straight in `src/` or in a folder that is not a layer, and `munch/folder-imports` fails an import across the lines below.

- **The layers, top to bottom, one way.** `app/` (the root component's wiring) over `screens/` (one folder per screen) over `features/` over the shared client layers, `ui/`, `domain/`, `render/`, `art/`, `audio/`, `input/`, and `platform/` (one layer: they import each other freely, short of a cycle) over `world/` over `shared/`. `munch/folder-imports` fails an import of a higher layer, an import of one screen from another, and an import of one feature from another, as in Feature-Sliced Design (its widgets and pages are our screens).
  - **`app/`** is the root's wiring only: the Model, Commands, Mounts, Subscriptions, the root view that places each screen and draws its children with their props and events (`views/lobbyView.ts`, `views/coopView.ts`, `views/profileView.ts`), the root's own Dialogs (each shell around the insides its screen draws, in `menus/`), and every root handler in `app/update/` with the Steps they share, a plain feature's too (`home.ts`, `end.ts`, `onboarding.ts`). Anything that needs a Mount or a root Step stays here; a screen gets it handed in (the menu panel takes the Munchopedia's view, the end card's SHARE takes the ShareFromClick Mount).
  - **`screens/`** puts several features together into one screen: `screens/home/` (the home menu, its hand and panels, the install tile, the update gift) and `screens/game/` (the game surface in every phase: the world scene, the HUD, the overlay, the touch controls, Rattles' bubble, and the buttons over the game). A screen imports any feature and any lower layer. A new screen is a new folder; what two screens both need goes down to a feature or a shared layer.
  - **`features/`** is one folder per thing on screen, apart from the others.
  - What two features both need goes down to the layer they share: a client rule or Schema to `domain/`, an HTML part to `ui/`, canvas drawing to `render/`, pixel art to `art/`, the store and sync to `platform/`, a pure helper to `shared/`.

  The rule has two exceptions, each listed in it with its reason:
  - **The root's types.** `import type` of exactly the root's `Model` (`app/model.ts`) and its view aliases (`ApplicationViewBuilder`, `ApplicationHtml`, and `ApplicationMount` in `app/component.ts`), never a value and never another name from those modules: a feature's rules and views, and the client layers' drawing, read the root's one Model, and a view sends the root's Messages. Narrow a function to `World` or to the fields it reads where that is honest, rather than adding to them.
  - **A parent component and its child.** A feature imports another only as a parent importing the contract of a child it draws: the child's `block.ts`, `model.ts`, and `message.ts`, straight in its folder. The pairs are the rule's `CHILD_BLOCKS`: the solo lobby and co-op draw the hero picker (`heroes`), and the Munchopedia draws the guide to the house's finds (`guide`). A child's own children in its `blocks/` folder are the same feature (the Profile's Look tab). A new pair joins the list with its reason; anything else a parent needs of a child (an id its opener wears, a picture) moves into the child's contract or down a layer.

- **Import across folders through the layer's subpath.** `package.json` maps each layer to a subpath import (`#world/*` to `./src/world/*`, and so on for every layer), so an import in `src/` that leaves its own folder names the layer, `#world/step/stepWorld.ts`, never `../step/stepWorld`, and one within its folder or below stays relative, `./keys.ts`. Every relative or subpath import names its extension. `munch/subpath-imports` fails a `../` import that stays in `src/` and an import with no extension; oxfmt sorts the subpath imports into their own group. Imports that leave `src/` (`../../../CHANGELOG.md?raw`), the tools' imports into `src/`, and CSS `@import`s stay relative. A tool in `tools/audit` or `tools/video` imports the game as `@game/...`.
- **Split a big folder by role.** A layer or a feature with more than about eight modules groups them in subfolders, each a single role or subject: `views/` for view functions and canvas art, `machines/` for effect-machine flows, `mounts/`, `services/`, and subjects such as `render/camera/` or `platform/save/`. A component's contract files (`block.ts`, `model.ts`, `message.ts`, `update.ts`, `view.ts`) and its styles stay at the top of its folder, as do a feature's plain rules. A test moves with the module it tests into that subfolder's `__tests__/`. A new module joins the subfolder of its role, and its row joins that folder's group in the layer's `README.md`.
- **A root Message and its handler go with the feature that sends it.** The root's Message union in `app/message.ts` is one flat `UiSchema.TaggedEnum` of every group's cases, so `Message.X(...)`, the save, and the tools see one union. A group is a cases record and its own union in the sending feature's `message.ts` (`inputCases` and `InputMessage` in `src/input/message.ts`, `homeCases` and `HomeMessage` in `src/features/home/message.ts`, co-op's in `src/features/coop/message.ts`; the browser's and the Worker's in `src/platform/message.ts`), and that feature builds and types its Messages from it (`HomeMessage.ClickedPlayButton()`). A child component's events come up as the root's own Messages, mapped in the view's `onEmit` and named after the child (`PickedLobbyHero`). A new root Message joins a group (or a new group, spread into `app/message.ts` and listed in `src/app/__tests__/message.test.ts`, which fails a tag two groups both name). Its handler joins that group's `defineHandlers({...})` record (`src/app/update/step.ts`) beside the Steps it calls, in `src/app/update/`, since a handler calls the root's Steps and a feature imports nothing of `app/`: a feature's own in `app/update/<feature>.ts` (`homeHandlers` in `home.ts`, `endHandlers` in `end.ts`, `onboardingHandlers` in `onboarding.ts`), the rest by what they handle (`inputHandlers` in `input.ts`, `saveHandlers` in `save.ts`, ...), and a child's events in that child's `app/update/<child>.ts` (`lobbyHandlers`, `coopHandlers`). `app/main.ts` spreads every record into its one exhaustive `ApplicationDef.update({...})`, so a Message with no handler fails typecheck there.
- **`src/world/` is what the co-op room loads.** It imports only `src/world/` and `src/shared/`, Effect, Effect UI's root module (`UiStruct` and `UiSchema`), and the netcode package's types; `src/shared/` imports only itself (`munch/folder-imports`). `bun run world:check` fails any game module outside those two folders in the room's bundle, and in infra's types but for the few infra serves (`INFRA_OWN_MODULES`: the player log's events and projection, analytics, and the recordings API). A rule the room runs goes in `world/`; a client rule, view, or Step goes in a client folder. Name a feature's folder after its `world/` folder where both exist (`world/shop` and `features/shop`, the hold to buy and its tags).
- **One folder per thing on screen** in `features/`: its view, styles, and client rules, and a component's own update. A plain feature's Steps on the root Model and its handlers live in `app/update/<feature>.ts`. A new feature is a new folder.
- **A folder that holds a component uses the component file names**: `block.ts` (the component, `Html.component(...)` made with `make`), `model.ts`, `message.ts`, and, where they are apart, `update.ts` and `view.ts`, with `__tests__/` holding its `story.test.ts` and `scene.test.ts`. A component's child components go in its own `blocks/` folder (the Profile's Look tab, `features/profile/blocks/look/`). Props go down and events go up: the root owns what the root reads (a dialog's `isOpen`, whether the lobby is up, the picks, the Profile's state, the co-op room) and hands it down as props, a child owns only what nothing else reads (the Munchopedia's guide, the shelf's picked slot, the Look tab's little tab), and a child's events say what happened for the parent to judge ("Children" in `docs/EFFECT_UI_PORT.md`). The root's Steps that act on a child's events live in `app/update/<child>.ts` (`coop.ts`, `profile.ts`, `lobby.ts`), not in the child's folder. The hero picker (`features/heroes/`) is one component drawn by two parents, the solo lobby (`features/lobby/`) and co-op, so it stays a sibling folder rather than either one's `blocks/`, and the guide (`features/guide/`), drawn by the Munchopedia (`features/munchopedia/`) on its Shop page, keeps its own folder too. Co-op (`features/coop/`) is lifted to the root: its Model is the root's `coop` field, its Messages a group of the root's, its Commands and Subscriptions the root's, and its views view functions over the root's `h`. Add no `index.ts` barrel. The root uses the same names: `component.ts` for the component as defined, `block.ts` for it made, and `commands.ts` for its Command services.
- **Tests sit in `__tests__/`** in the folder that holds the code they test (`src/world/keys/__tests__/keys.story.test.ts`), with the fixtures only that folder's tests use (`boss.fixture.ts`). This keeps the tests apart from the code on purpose, so a folder lists its modules first. Setup several folders' tests share lives in `src/test/`. Shipped code never imports `src/test/` or a `__tests__/` folder (`munch/folder-imports`), and a module that is not a test or a fixture never sits in `__tests__/` (`tools/lint/folders.ts`). The rule covers `src/` only: the packages keep their `test/` folders and the tools their tests beside their scripts.

### Rules

- **Keep the game deterministic.** `update` is pure. It never calls `Math.random` and never reads the clock. Randomness comes from the seeded generator whose state lives in the Model, so the same seed and the same Messages give the same game. It also plays bit for bit the same in every engine (Bun and Safari's JavaScriptCore, Node, Chrome, and workerd's V8), since recordings replay in Bun and Node and the co-op room steps in workerd: the World, the input, the update, the features' rules, and the lens take `sin`, `cos`, `atan2`, `hypot`, `exp`, and the like from `src/shared/detMath.ts`, never Math's own, whose last bit each engine rounds its way, and never `**` but on the literal 2 (`munch/stable-math`). CI's `determinism:ci` plays a run in Bun, Node, and workerd and fails on the first bit they disagree on.
- **Model a flow with states as an effect-machine machine.** A client flow with states (the device link, co-op's screens, the root's dialogs, the audio engine, a friend's dare, the splash, the update gift, the first-run question, the tutorial reset) is an effect-machine `State` and `Event` table built with `Machine.make`, held on the Model and folded in `update` with `machineStepOf` (`src/domain/machines/machineStep.ts`), so it stays pure and deterministic. A result is accepted only in the state that waits for it, a Command starts on entering a state, and each machine has a coverage test over `Machine.definition`. An actor runs only async connection work that nothing deterministic reads. The World is never a machine. See [`docs/EFFECT_MACHINE_PLAN.md`](./docs/EFFECT_MACHINE_PLAN.md).
- **Support desktop and touch.** Every input must work with a keyboard and mouse and with touch. Touch tracks each finger by its `pointerId`, so two thumbs work at once.
- **Buttons act on OnClick.** `src/input/touchTaps.ts`, mounted on the game's root, turns each finger's tap into a click from its own pointer events, so a button works with another finger on the glass and acts once. Never act on a touch or mouse release (`munch/tap-by-click` fails `.on('touchend', ...)`, `pointerup`, `mouseup`, and the like); `.on('pointerdown', ...)` is for acting the moment a finger lands. An animation never moves a button or what holds one: it fades or flashes in place, and only art inside moves (`src/app/__tests__/motion.test.ts`).
- **Support portrait and landscape on phones.** A touch phone held upright plays in the portrait layout (see "Portrait play" in `docs/GAME_DESIGN.md`). Overlay code reads the screen from `screenOf(model)`, never `VIEW_WIDTH` and `VIEW_HEIGHT`, and CSS reads `--screen-w`, `--screen-h`, `--world-top`, and `--frame-top` (the top of the banners' frame) from `.game-root`, with `[data-layout='Portrait']` rules for portrait. Check a layout change with `tools/audit/shots34.ts` and `PORTRAIT=1 bun taps.ts`. The installed Android app starts in landscape and turns only when Settings' ROTATE is on (see "Rotation" in `docs/GAME_DESIGN.md`).
- **Follow the design doc.** Choices under "Decided" in `docs/GAME_DESIGN.md` are settled. The "Reference notes" are ideas, not decisions. If a change goes against a decision, say so before making it.
- **Show, don't explain.** Fewer words, more visuals. Prefer icons, art, motion, and sound to text, keep every label and line short, and never repeat what a player has already seen. Write new copy that way, and trim old copy you touch. See "Show, don't explain" in `docs/GAME_DESIGN.md`.
- **Use original art and names.** Do not copy art, names, or item lists from Zombie Estate 2.
- **Use Effect fully.** Reach for Effect's own APIs (Schema, Match, services, resources, `effect/sql`) rather than working around them. Keep the `@effect/language-service` plugin in `tsconfig.base.json`: without it `typecheck` still passes but reports no Effect problems.
- **Draw fixed art as sprite images.** A pixel map goes through `spriteShapes`, and a fixed list of whole pixel rectangles goes through `bakeShapes`. Build them once at module scope or in a cache, never per frame. A production build packs every sprite into a prebuilt atlas (`tools/sprites/`, see `docs/IMAGES_PLAN.md`), found by content key, so the game draws cropped regions of a few PNG files instead of encoding one per sprite. A sprite built lazily, on first use, must be listed in `src/art/atlas/spritePrecompile.ts`, or `tools/sprites/atlas.test.ts` fails. HTML that shows a sprite as an `<img>` takes `standaloneSource(image)`, since an `<img>` cannot crop. Tests draw stand-ins instead of PNGs (`src/test/vitest-setup.ts`). Shapes that change every frame, such as particles, bars, and decals, stay `Rect` shapes. **Every fixed sprite that stands is also a carved volume**, a block a pixel: the 3D renderer stands each one carved, never as a flat billboard. Its default form comes off its front art alone (`formOf` in `src/art/carve.ts`, round, an outline on the front face only), leaned along the camera's ray so the lens sees the art exactly (`lensFormOf` in `src/render/iso/bodies/voxelShape.ts`), its depth capped by what it is (`MOST_DEPTH` and `FURNITURE_MOST` in `src/render/iso/scene.ts`). A piece that reads wrong that way gets top and side views by part and hand fixes as a module-level `SpriteCarve` beside its pixel map, carved with `carveSprite` (the chandelier, `src/render/room/chandelierCarve.ts`). A carve is built on first use and cached by its content key, never per frame. Floors and walls are not carved.
- **Read the map from the level.** The map is data: the Model's `level` names the level, which hand-made room its run rolled into each slot (`arrangement`, from the seed), and its open exits, and `levelOf(model)` hands back the built `Level` with its tile lookups, doors, thresholds, and spawn doors. Every function that reads tiles, doors, or the level's size takes that `Level`. Only a fresh run (which starts in the parlour) and the stall (which stands there) read `PARLOUR` directly. Tile queries read `level.tileFlags`, one byte per tile (`hasTileFlag`). Tables derived from the map key on the `Level` (a new record whenever an exit opens), as the pathing tables and the room canvas do; the flow field is asked for on the frame and kept by the level, its origin tiles, and its tolls, a few at a time (`fieldFrom` in `src/world/level/pathing.ts`).
- **Keep the frame cheap.** `src/render/__tests__/perf.scene.test.ts` budgets the `Draw` shapes and paint operations of a full room, and `bun run perf:check` gates frame time against a recorded baseline (see `tools/audit/README.md`). `bun run perf:gpu` gates the GPU's side, which heats a phone while a desktop's frame time hides it: a room fill draws its shadow map again only when a caster in its cone changes (`src/render/iso/quality/shadowWatch.ts`), so a new caster outside the voxel batch must be noted there, and a break may draw almost no shadow map; in a wave at most two maps are drawn a frame (`src/render/iso/quality/shadowBudget.ts`). Two tests catch a cost before it shows in frame time: `src/world/__tests__/workBudget.test.ts` holds a stretch of a wave to a count of flow field searches and map scans (`countWork` in `src/shared/workCount.ts`; count a new pass over a whole level or plan there), and `src/world/__tests__/scaling.sim.test.ts` fails a step whose zombie share grows much faster than the crowd (a pass of every zombie against every zombie). Keep what a level or a plan derives in a cache keyed by it (`tilesWithSymbol`, `coverBlocks`, `fieldFrom`, `routeSpawns`), so a frame asking again costs a lookup. In code that runs every frame, check a union's tag with `isAnyOf`, not `guards`: a guard validates the whole value through Schema, and `Phase` carries the wave's spawn list. Three lint rules catch quadratic work: `munch/no-append-in-reduce` fails a reduce that copies its accumulator list each step (fill a local array in a loop, or use `Array.flatMap` or `filterMap`); `munch/no-deep-equal-per-frame` fails `Equal.equals` and Schema's equivalences in the per-frame code (`src/render/`, `src/screens/`, the frame's `src/app/` modules, `src/world/step/`, `src/world/zombies/`); and `munch/no-nested-scan` fails a scan of one list inside a loop over another in the World's per-tick folders and `src/render/`. Index the inner list once (a `Map` or `Set` built before the loop), even a list with a small bound (4 seats, 8 traps, 13 doors). Keep the Model and the World at 128 fields or fewer (`src/app/__tests__/modelWidth.test.ts`): engines copy a wider object about 17 times slower, and the frame copies both many times. A new client field joins one of the Model's groups (`settings`, `cosmetics`, `saving`, `runGains`, ...) once the top level is near the limit. The client hands `stepWorld` its World alone, `stepWorld(worldOf(model), inputs)`, so each write in the step copies the World's fields and not the Model's (`munch/step-world-alone`).
- **Stand what a body owns on its body, and anything standing through `standingPointOf`.** What shines on a body (the muzzle flash, the knife's slash) is a `Glow` drawable on its player's own plane (`playerFlashDrawable`), never overhead, so in 3D it moves with the body at every angle. Anything standing in the 3D world, a billboard, a voxel body, or a light, stands through `standingPointOf` in `src/render/iso/space.ts`, given the game pixel its sprite draws, never a height tuned by eye; `munch/stand-through-space` fails a module that imports the camera's up or its way toward the lens to do it by hand. The flash's middle is read off the gun's art (`gunTipOf`), and `src/render/__tests__/muzzleFlash.test.ts` holds it just past the drawn tip for every gun and facing.
- **Persistent data goes through the store.** Anything that must last across reloads goes in `PlayerSave` (its Schemas in `src/shared/records/playerData.ts`, the rest in `src/platform/save/save.ts`), with a bump of `SAVE_VERSION` and a migration or a fallback to no save for the older version. Add it to `saveOf` and `restoreSave`. `update` then writes it on change through the `WriteSave` Command, which goes through `PlayerStore` in `src/platform/save/store.ts`. Never touch SQLite, OPFS, or `localStorage` anywhere else. Other SQLite code goes through `@munch/sqlite-wasm-effect` (see its README).
- **Player data changes go through the player log.** The save is an `effect/eventlog` log per player (`src/platform/save/playerEvents.ts`), synced to the Worker's `PlayerLog` Durable Object: a change to it is an event, never a direct write to the save's tables. A new kind of change gets a `PlayerChange` case and its place in `changesBetween` (`src/platform/save/playerSync.ts`), an event in `PlayerLogSchema` (a field of the last-writer-wins `PlayerRow` when the last one set should win, its own event when two devices can both change it), its handler in `src/platform/save/playerProjection.ts`, and its case in `writtenOf` in `src/platform/save/storeSqlite.ts`. A handler merges in any order and twice to the same save (increments rather than totals, the larger of two bests, a first stamp kept): `src/platform/save/__tests__/playerProjection.test.ts` applies two devices' events both ways. Never change a shipped event's payload but by adding an optional field. The same files run in the Worker, so keep them to `effect` and `src/shared/`. See "What phase 4 built" in `docs/PLATFORM.md` and `docs/EVENTLOG_MIGRATION.md`.
- **Send analytics only through SendRunSummary.** The summary is built in `update` from the Model (`src/platform/analytics/analyticsRun.ts`), the network call lives in the Command, and nothing is sent when "Share anonymous play stats" is off. A new field goes in `RunSummary` in `src/platform/analytics/analytics.ts` with a bump of `RUN_SUMMARY_VERSION`, and a new D1 migration in `infra/migrations`. Nothing personal goes in a summary.
- **Write tests for game logic** as Story tests that replay Messages. Break the code once to see the test fail before you trust it.
- **Keep `bun run test` fast.** A test that plays more than about one wave of game time, or takes more than 300 ms, goes in a `*.sim.test.ts` file beside its Story test, which only `test:full` and CI run. A file that needs a page (it builds elements, dispatches window events, or uses `localStorage`) is named `*.dom.test.ts`, which `vitest.config.ts` runs in happy-dom; the rest run in plain Node, and Scene tests always get a page. Files share a worker's modules (`isolate: false`), so a test that changes a global (a spy, a stub, `localStorage`) puts it back in `afterEach`. The nightly workflow runs `test:full` in a shuffled order to catch one that does not. CI's four test shards split the files by their time, not their count, and each run starts its slowest file first (`tools/vite/testSequencer.ts`): a new file of 2 s or more joins its `FILE_MS` table, and a shard that runs well past the others means the table wants refreshing from a CI log. See `vitest.config.ts` and `docs/TESTING_PLAN.md`.

### Components and dialogs

The root and its children are Effect UI components (`docs/EFFECT_UI_PORT.md`, and Effect UI's guides in `repos/effect-ui/ai-docs/src/10_ui/`: `10_basics.ts`, `21_view-functions.ts`, `24_mounts.ts`, `25_document-events.ts`, `27_state-ownership.ts`, and `50_testing.ts`).

- **The root is split by role**, in `src/app/`. `component.ts` holds `ApplicationDef` (`Html.component({ name, model, message })`) and the view aliases, `main.ts` init and `update` over the handler record, `view.ts` the view, `subscriptions.ts` and `mount.ts` the Subscriptions and Mounts, `block.ts` the component made (`ApplicationNoDeps = ApplicationDef.make({...})`) and `Application`, it with its Command services provided, `commands.ts` `CommandsLayer`, and `services.ts` `ApplicationLayer`. `entry.ts` only mounts `Application` on the page.
- **Props down, events up.** A child component (the solo lobby, the hero picker, the Profile and its Look tab, the Munchopedia, the Proof Shelf) is drawn by its parent's view with its props, and says what happened with an event (`Picked`, `RequestedBuy`, `RolledNameDice`) that the parent maps in `onEmit` to its own Message, named after the child (`PickedLobbyHero`, `RequestedCloseHeroPicker`). There are no requests from parent to child: a parent changes a child's props, or its `key` to start it afresh (the Proof Shelf each time the panel opens on it). State that a root rule, `menuState`, the save, or a root test reads is the root's, on its Model, handed down as props; a child's own Model holds only what nothing else reads. Anything random a child needs the root rolls from its seeded generator and hands down (`RolledNameDice`, then the name as a prop), so every update stays deterministic. Content a parent puts inside a child (the menu panel's Done in the Munchopedia and the Proof Shelf) is a slot, `slots: ['done']` and `h.slots.done`.
- **The root's dialogs are one machine on the Model**, `rootDialog` (`src/app/menus/rootDialog.ts`): Shut, or the one dialog up (Profile, Panel, Hand, HomeScreenSteps, UpdateGreeting), so two are never open at once and a close names the one it closes. Each is drawn ui-kit's `Dialog` through `dialogShellView` (`src/ui/dialog.ts`) in `src/app/menus/dialogs.ts` and `src/app/views/profileView.ts`. Open one with `openRootDialog(name)` and close it with `closeRootDialog(name)` (`src/app/update/dialog.ts`); a close the dialog asks for (Escape, a press outside, its close button) arrives as `ClosedDialog({ dialog })`, and a close keeps the Profile's name or forgets the panel's question. `munch/no-dialog-field-write` fails an `evolve` or `set` that writes `rootDialog` anywhere else in `src` outside tests; a new root dialog joins `RootDialog`, `DialogName`, and `MenuState` together. Its insides take the kit's parts (`DialogParts`: `title`, `description`, `close`, `initialFocus`). A child's own dialog (the solo lobby's hero Dialog) is ui-kit's `Dialog` in the child's view, open on a prop.
- **A Step is a function of the update `$`.** `UpdateStep = ($: App$) => Model | AppStep` (`src/app/update/step.ts`): it returns `$.model` when it changes nothing, `$.evolve({...})` or `$.set(next)` for a new Model, `.run(X.make(args))` for Commands, and `$.combine(a, b)` (or `combine([a, b])` as a Step) to run Steps in turn, each reading the Model the one before it left. A Step reads `$.model`, never a Model captured before an earlier Step in the same `$.combine` ran. Build a Step that only changes the Model with `modelStep(change)`; a Step that needs arguments is a factory, `(x) => UpdateStep`, not a dual.
- **Every change settles once.** The after-message Steps (`afterMessage` in `src/app/update/settle.ts`: music, end focus, rotation, Nightmare, the run count and summary, the save) run once after every Message, a child's event included: `update` in `main.ts` is `($, message) => $.combine(handle, ...afterMessage($.model, mode))`, where `handle` is `ApplicationDef.update({...})` over every group's handlers and `mode` is `Synced` for the synced saves and `Write` for the rest. A handler holds only its own change and never settles itself. Each Step acts on a change between the two Models and reads only the root's fields, so a Message that leaves the root as it was costs little and does nothing. A new Message whose change must not be written back joins `SYNCED_SAVES` in `main.ts`.
- **Commands and Subscriptions.** A Command is `Command.make(name, { args }, args => effect)` when it needs only the browser or nothing, or `class X extends Command.Service<X>()('app/X', { args, success, mode? }) { static readonly layer = this.toLayer(...) }` when it needs a service, its `.layer` joined to `CommandsLayer` in `commands.ts` (`AppHandlers` is read off it). It is defined beside the update that returns it and issued with `X.make(args)` inside `$.run(...)`. Its body handles its failure itself and returns a Message, or `Component.noop` when nothing is to be reported; `mode: 'switch'` for a check whose newer run replaces the older, `'queue'` for writes that go in order (the save). A Subscription is `Subscription.make(name, deps, () => stream)` or an `HtmlSubscription` (frames, shortcuts, document events), listed by `subscriptions: ({ model }) => [...]`; a Mount is `Mount.make(name, { args }, (node, args) => effect)`, placed with `.onMount(X(args))`.
- **Tests drive the root through Stories and Scenes.** A root test is `it.effect` from `@effect/vitest` over `Effect.gen`, with `const s = yield* Story.make(ApplicationNoDeps, {})` (or `HtmlScene.make` from `@effect/ui/html/testing` for a Scene), then `s.given(model)`, `s.send(message)`, `s.resolve(Command, message)`, `s.expectExact(...)`, and `s.model`; `storyOf(model)` and `sceneOf(model)` in `src/test/testing.ts` start one from a named Model with its audio asked for, and `exactStoryOf` and `exactSceneOf` from the Model as it is. `ApplicationNoDeps` (`src/app/block.ts`) is the root with no Command services: a Command never runs in a test, so it needs none of them. The shared steps in `src/test/testing.ts` (`tick`, `ticks`, `press`, `tap`, `send`, `startWave`, ...) and `src/test/sceneTesting.ts` (`fromSubscription`, `emitPressedKey`, `emitFrame`, the surface's measure and presses) are functions over the cursor, `steps(...)` runs several as one, and `RootSteps` types a group held apart, such as a table's row (`src/app/update/__tests__/seatAction.parity.test.ts`).
  - **Every Story is yielded.** `Story.make`, `Scene.make`, `HtmlScene.make`, and `HtmlPlay.make` are scoped Effects: a Story built and dropped never runs, its steps never throw, and its end check never fails. Loop with `yield* Effect.forEach(...)`. `munch/no-floating-story` (in `tools/lint/testRules.ts`) fails one that is not yielded, returned to `it.effect`, or handed to an Effect combinator: in `Array.forEach`, a plain `test`, or a statement.
  - **Commands.** A Story ends with every Command resolved and every event acknowledged: its end check runs as the test's scope closes. A message step throws while a concurrent Command is pending, unless the Command's mode is `switch` or `queue` or the step says `keepPending`. `Story.start` and `HtmlScene.start` make a cursor with no end check, only for a step that must throw, inside the assert that says so; `munch/no-plain-story` fails one anywhere else.
  - **A child component's own behavior** is tested on its own, `Story.make(Child, props)` with `s.emitted(event)` for what it sends up; a parent's view of a child's event is `s.childEmit(Child, event)`.
  - **`src/app/pureApp.ts` is for the tools**: the balance bot, the determinism tools, the audit harness, and the sprite atlas play the game through it. Tests read its `initialModel` (the whole start Model, behind the named Models of `src/test/model.fixture.ts`) and nothing else; `munch/no-plain-story` fails `update`, `view`, or `init` imported as a value from it or from `src/app/main.ts` in a test or its shared setup.
- **A new Model field joins `tools/determinism/fields.ts`**: a child's field is `Client`.

### Strictness

`typecheck` and `lint` are strict on purpose, so the easy way to write code is the right way. Every project extends `tsconfig.base.json`, the tools too: they are held to the game's rules.

- **`typecheck`** is strict TypeScript plus unused locals and parameters, `override`, no switch fallthrough, erasable syntax only, `import type` for types, and bracket access for index signatures (`process.env['X']`). Every Effect language service diagnostic is on, at error (see "Effect, all rules on" below). `typecheck` runs the Effect-patched `tsrs` (`effect-tsgo tsrs`) on each project. `lint` reports the same diagnostics in its one pass (oxlint's `--type-check`), each file under the tsconfig nearest it, plus `tools/vite`'s project with `tsrs`, since `vite.config.ts` and `vitest.config.ts` sit beside the root's tsconfig but belong to `tools/vite`'s. So the program is built once, and CI runs no separate typecheck.
- **`lint`** is oxlint's correctness and perf categories, type-aware rules (floating promises, exhaustive switches, no unsafe `any`, strict booleans), the project's own rules, and every Effect rule (`.oxlintrc.effect.json`: the strict preset plus each rule it leaves out), run as one pass through `.oxlintrc.all.json`, which extends both. The two stay apart so stock oxlint and editors can read `.oxlintrc.json` without the effecttsgo plugin; a rule goes in one of them, never in `.oxlintrc.all.json`. The pass runs its type-aware rules on the Effect-patched `tsrs` (`effect-tsgo --tsrs-lint oxlint`), not tsgolint. In `src` it also enforces the Rules above: no `Math.random`, `Date.now`, `crypto.randomUUID`, or `Data.taggedEnum`, no `.guards` outside tests, `performance.now` only in `subscriptions.ts`, storage only in the store, and no `VIEW_WIDTH` or `VIEW_HEIGHT` in overlays. In the tools and the packages it bans `Math.random`, `Date.now`, `Data.taggedEnum`, `setTimeout`, `setInterval`, and `fetch`. The project's own rules live in `tools/lint/munchPlugin.ts` (the rules about tests in `tools/lint/testRules.ts` and about quadratic work in `tools/lint/perfRules.ts`, imported by full file name, since oxlint loads the plugin in Node), an oxlint JS plugin in TypeScript over `@oxlint/plugins`' typed AST, which the root and `infra` configs both load and `tools/lint/munchPlugin.test.ts` runs on code each rule must and must not flag: `munch/no-tag-chain`, `munch/no-extract-tag`, `munch/no-raw-json`, `munch/no-conditional-step`, `munch/no-world-spread`, `munch/no-menu-field`, `munch/command-beside-update`, `munch/no-run-in-tests`, `munch/no-floating-story`, `munch/no-plain-story`, `munch/tap-by-click`, `munch/seat-action-once`, `munch/key-action-once`, `munch/stand-through-space`, `munch/no-dialog-field-write`, `munch/folder-imports`, `munch/subpath-imports`, `munch/no-append-in-reduce`, `munch/no-deep-equal-per-frame`, `munch/no-nested-scan`, `munch/step-world-alone`, and `munch/no-comments` (see "Code shape" and "Components and dialogs"). A new rule gets its cases there. No file anywhere has an em dash (`tools/lint/noEmDash.sh`), no file is over 1200 lines (`max-lines`, in the root and `infra` configs), every module in `src` has its row in its layer's `README.md` (`tools/lint/fileTable.ts`) and sits in its layer's folder, its tests in `__tests__/` (`tools/lint/folders.ts`), and no helper is copied between files (`tools/lint/duplicateHelpers.ts`, see "Code shape"), and nothing is dead: `knip` (`knip.jsonc`) fails an unused file, export, type, or dependency in `src`, the packages, `infra`, and the tools.
- **The tools follow the same rules**, and so do the build and test configs (`vite.config.ts`, `vitest.config.ts`, the harness's), linted with the tools and typechecked in `tools/vite`. No `any`, no `as`, no `!`, strict booleans, JSON through Schema (`tools/json.ts`: `readJsonFile` and `writeJsonFile` as Effects over `FileSystem`, `decodeJson`, `encodeJson`), and Effect's clock, timers, `HttpClient`, `Schedule`, `Console`, `Config`, `FileSystem`, `Path`, and `ChildProcess` in place of `Date`, `setTimeout`, `fetch`, polling loops, `console`, `process.env`, and `node:fs`, `node:path`, and `node:child_process`. A script is an Effect program from end to end. An audit reads the page through the typed globals in `tools/audit/page.ts` (`window.__model` is the game's `Model` inside `page.evaluate`) and brings a value back out with `evaluateAs(page, schema, fn)` or `modelAs(page, schema)`, a Schema of only the fields it reads. A timing audit reads the wall clock with `nowMs()` from `tools/audit/lib.ts` (Effect's `Clock`) and polls with `pollUntil` (a `Schedule`). Code that runs inside the page, where Effect is not loaded (its own timers, `fetch`, `requestAnimationFrame`, async functions, and native array, string, and record methods), lives in a tool's `inPage/` folder (`tools/audit/inPage/`, `tools/video/inPage/`): each function stands alone, with no imports, and is handed to `page.evaluate` by reference. The configs' `tools/*/inPage/*.ts` overrides are the only place those rules are off.
- **No comments in code.** `munch/no-comments` fails every comment in a JavaScript or TypeScript file: line, block, doc, and directive comments alike. Name the code so it reads on its own (a function, a constant, or a type that says what it is for), and say why in the commit body. A rule is never silenced in place: no `oxlint-disable`, `@effect-diagnostics`, `@ts-expect-error`, triple-slash reference, or `@vitest-environment` comment. Fix what a rule flags. Where a rule cannot hold for a whole kind of file (the service worker, a tool's `inPage/` code, a component Effect UI makes), turn it off by an override in the config, with the reason as a comment on the override: the JSON configs (`.oxlintrc*.json`, `tsconfig*.json`) are the one place comments stay.
- **Effect, all rules on.** Every `@effect/language-service` diagnostic is at error in `tsconfig.base.json`, and every Effect oxlint rule in `.oxlintrc.effect.json` (and infra's), with none turned off. Where they disagree with `docs/EFFECT_UI_PORT.md` or Effect UI's guides, they win: a Command's fallback Message is `Effect.orElseSucceed(...)`, not `Effect.catch(() => Effect.succeed(...))`. What they ask of code:
  - An exported function of two or more fixed arguments is dual: a data-first and a data-last call signature, built with `Function.dual(arity, impl)` (`missingPipeableSignature`). When an optional argument makes the count ambiguous, tell the two forms apart with a cheap test from `src/shared/dualArgs.ts`, or make the argument required. Pass a dual function to a callback through a lambda, never point-free: `Array.map` passes an index too.
  - Native array, string, and `Object` methods go through effect's `Array`, `String`, and `Record`, imported under those names from `effect` (the global is then `globalThis.String`). `findFirst`, `indexOf`, `charAt`, and the like return an `Option`.
  - A number in a Schema is `Schema.Finite`, not `Schema.Number`.
  - An error is a `Schema.TaggedError` class built with `.make`; `Effect.try` and `tryPromise` have a `catch`; Schema decodes through its Effect, Option, or Result forms, not `decodeSync`; a Layer is built in the program's scope, not `Effect.provide`d along the way; and no `yield*` sits in a call's arguments.
  - An unstable Effect API is allowed by its module in `allowedUnstableApis` in `tsconfig.base.json`. Our own exports carry no stability tags (`apiStabilityLeak` is off, with its reason in the configs); still keep an unstable type out of an export where you can, as `src/platform/coop/lobbyWrite.ts` keeps `Mutation` out of `RoomAccess`.
  - Effect rules are off only by config override, where Effect cannot be used: the service worker (`src/platform/sw/worker.ts`, which loads no modules), code that runs inside a tool's page (`tools/*/inPage/`), and a component as Effect UI makes it, which has no data-last form (each `block.ts` listed in the `missingPipeableSignature` override in both configs). The root's `view` and `update` are dual (`Function.dual(2, ...)`), as Effect UI accepts either form.

### Code shape

- **Match every union exhaustively**, with the Schema union's `.match` or `Match.valueTags`, not an if/else chain on `_tag` that ends in a catch-all. When only some variants matter, say so: the union's `.matchOrElse`, or `Match.value(x).pipe(Match.tag(...), Match.orElse(...))` for a union with no Schema, such as `Draw.Shape` or Effect's `SchemaAST`. `munch/no-tag-chain` fails two or more `_tag` checks on one value in a row (or on a tag held in a variable named `tag` or `...Tag`): `else if`, early returns, or nested ternaries. A lookup by tag is a record typed over the union's tags (`{ readonly [Tag in ServerFrame['_tag']]: ... }`), so a new variant fails typecheck until it has its entry. One check alone is fine. In per-frame code, keep a single check or `isAnyOf` cheap: build no handler object per entity per frame.
- **Keep the client out of the World's types.** A module the co-op room reaches (`stepWorld.ts`, `roomWorld.ts`, and what they import) imports a World type from where it is declared (`worldSchema.ts`, `entitySchema.ts`, `wireNumber.ts`), never through `model.ts`, and never takes the client `Model`, not even by `import type`. A rule that reads only World fields takes a `World`, or `<M extends World>(model: M): M` built with `modifyWorldFields` (`src/world/schema/world.ts`) so single player gets its own Model back; one that reads a client field lives in a client module (`frame.ts`, `home.ts`, `src/app/update/`). Such a module lives in `src/world/` or `src/shared/`, and `munch/folder-imports` and `bun run world:check` keep the client out of it ("Folders").
- **A player's state lives in `seats`, and a per-player rule takes a slot.** The World holds one `SeatState` per player (the seat's record, `player`, `intent`, `boosts`, `trapStock`, `selectedTrap`, `laserSight`, `purchase`, `cooking`, `feats`) in slot order, single player's at `SOLO_SLOT`. A rule that acts for one player is `(world, slot, ...)`: it reads with `seatStateAt(world, slot)` and writes with `modifySeat(world, slot, {...})`, or `seats: atSeat(slot, {...})` among other World fields in one `evolve`. `forEachSeat(world, (current, slot) => ...)` goes in seat order and never rebuilds the World to put a seat in place. A screen reads the seat it is about with `focusOf(model)` (the first seat: the only one in single player, a co-op client's own after `focusSeat`) and writes it with `modifyFocus`; a rule that is about no one seat (the wave, the boss's room) reads no seat. A seat added to the World joins `SeatState` in `src/world/schema/worldSchema.ts`, which is a protocol change (`packages/netcode/src/Protocol.ts`).
- **Merge a World result with `withWorld`**, never `{ ...model, ...world }`. `munch/no-world-spread` fails a value named as a World (`world`, `nextWorld`, `x.world`) spread after the first spread.
- **Ask `menuState(model)` which menu is up** (`src/app/menus/menuState.ts`). It derives a `MenuState` from the dialogs, the lobby, co-op, and the phase, top first (Profile, Panel, Hand, InstallSteps, UpdateGreeting, HeroPicker, Lobby, Coop, then Home, Playing, Paused, or EndScreen; the lobby's own reads are `isLobbyShown` and `isHeroPickerUp` from `src/features/lobby/model.ts`), and is never stored. Update's gates and the view read it or its helpers (`isOnHomeMenu`, `isPanelOpen`, `isProfileOpen`, `isProfileOpenOn`, `isHandOpen`), so they agree. `munch/no-menu-field` fails a read of `rootDialog` and `model.coop.screen` anywhere else in `src` but tests (co-op's own routing reads `isCoopOpen`; a dialog's view asks `isRootDialogOpen`).
- **Define a Command beside the update that returns it**, not in a module of Commands: the Step that returns `WriteSave` and `WriteSave` both live in `update/save.ts`. Only the Commands init starts live apart, in `boot.ts`, which returns them as `bootCommands`. Every root `Command.Service`'s `.layer` joins `CommandsLayer` in `commands.ts`. `munch/command-beside-update` fails a `Command.make` or `Command.Service` class whose module never issues it (`X.make(...)`).
- **Run a Step on a condition with `stepWhen(isDue, step)`** (`src/shared/stepWhen.ts`, generic, so any component's update uses it), and build a Step that only changes the Model with `modelStep(change)` (`src/app/update/step.ts`). `munch/no-conditional-step` fails `cond ? step($) : $.model` (or `unchanged($)`, or `$.combine(...)` in the Step's place) either way round; a result built in place (`cond ? $.run(...) : $.model`) passes. When the condition narrows a union, match it (`Screen.matchOrElse`). To pick between Steps, pick the Step and run it: `(cond ? step : unchanged)($)`. Name a Step for what it does, with no `Step` suffix.
- **A player action's rule lives once, in stepWorld; single player calls it through withWorld.** Swapping, the knife, drawing a gun, reloading, traps, READY, and MEDIC! are `SeatAction`s, each decided once in `src/world/step/stepWorld.ts` (`trySeatAction`, `applySeatAction`), where the co-op room runs them too. Single player's handler applies one to its lead seat with `actAsLead` or `tryAsLead` (`src/app/update/action.ts`, over `withWorld`), keeps its client checks in front (the menus, the new zombie card), and wraps only its cues around it (sounds, `dropClip`, focus), read from the result or the refusal. Buying in the world (hold or stand to buy, with keys off the crew's ring: the boards, the fridge, a case's prize) rides in the intent and lives in the tick. `src/app/update/__tests__/seatAction.parity.test.ts` runs every action both ways from the same World, keyed by the union's tags, so a new action needs its row; `munch/seat-action-once` fails a rule's own steps (`swapInHand`, `beginReload`, `startWaveEarly`, ...) imported, or a seat's fields (`player`, `traps`, `trapStock`, `selectedTrap`) written with `evolve`, `modifyFocus`, `modifySeat`, or `atSeat`, in `src/app/update/`, `main.ts`, `runFlow.ts`, and `couch.ts`.
- **A key presses a seat action through one table**, `src/input/keyActions.ts`: `playerKeyAction(model, code)` for single player and co-op's client, `keyActionOf(seat, keys, code)` for a couch player's own keys. It also keeps READY's key, the interact key, from starting a wave at a purchasable, where it is held to buy. `munch/key-action-once` fails any other module that imports `isInteractTaken` to decide a key itself.
- **An online run's Messages go through `orInRun`** (`src/app/update/coopRun.ts`): the handler wraps its single player Step, `orInRun(message, swapFromButton)($)`, and `orInRun` checks `isRunOn` once and matches the Message. A new Message a co-op run handles its own way joins `RunMessage` there.
- **Read and write JSON through Schema** (`Schema.fromJsonString(schema)`, or `HttpClientRequest.schemaBodyJson` and `HttpClientResponse.schemaBodyJson` over HTTP), not `JSON.parse` or `JSON.stringify`. `munch/no-raw-json` fails them in `src`, the packages, and `infra`; the few files allowed are overrides in the configs, each with its reason.
- **Pack a World number on the co-op wire by its Schema.** A number with no `wire` annotation goes exactly. A lossy packing is named on the Schema (`PositionNumber`, `VelocityNumber`, `UnitNumber`, `MillisNumber`, and the `Point`, `Heading`, and `Push` vectors in `src/world/schema/wireNumber.ts`), never picked by field name. `src/world/net/__tests__/worldCodec.test.ts` lists every lossy number and pins the bytes of a scripted room: a change to either is a protocol change.
- **Describe a thrown value with `describeError`** (`src/shared/describeError.ts`), not a copy of `error instanceof Error ? error.message : String(error)`.
- **Retry and back off with a `Schedule`**, not a loop or a timer.
- **Name a variant once**: `type Turret = typeof Trap.Turret.Type` beside the union (`typeof Union.cases.Name.Type` for an Effect `Schema.TaggedUnion`, an `interface` member for a plain union), not `Extract<Trap, { _tag: 'Turret' }>` at each use. `munch/no-extract-tag` fails the `Extract` form.
- **Share helpers, never copy them.** Canvas shape helpers (`rect`, `pixelArt`, `centeredRect`) live in `src/render/drawing.ts`, HTML parts the menus and overlays share (`iconView`, `keyCapView`, `percentOf`) in `src/ui/menuParts.ts`, vector and timer helpers (`distanceBetween`, `OUTWARD`, `countDown`) in `src/world/step/geometry.ts`, and anything else in the module it is about (phase checks such as `isEndScreen` in `src/domain/run.ts`), exported from there. `tools/lint/duplicateHelpers.ts` (in `bun run lint`) fails a top-level function, or a constant built from an object, array, or call, that two modules of one code base (`src` and the tools, a package's `src`, infra's Worker) declare with the same body, where every name the body reads means the same thing. A copy under a new name fails too (`NO_PUSH` beside `ZERO_VECTOR`), so before writing a helper, find the one that already holds that value and import it. A script's own state (what it awaits, an empty list it fills, what it reads from its arguments, environment, clock, or `import.meta`) is never a copy. Its `ALLOWED` list holds the few copies left on purpose, each with a reason, and fails an entry that no longer matches.
- **Share test setup, never copy it.** Steps, locators, and builders of zombies, bullets, and guns live in `src/test/testing.ts`; the named Models a test starts from (`home`, `readyModel`, `quietWave(wave)`, `atFridge(keys)`, `withKeys(model, keys)`), the changes tests make to one, and spawns live in `src/test/model.fixture.ts`; a package's in `test/fixtures.ts`, the Worker's in `infra/worker/testing.ts`. Group a Story setup of several steps with `Story.steps(...)` and pass it whole (`tap(code)`, `finishSplash`), not as an array to spread. Keep the steps a test is about in the test itself: a fixture holds the state it starts from, never the behavior under test. `tools/lint/duplicateHelpers.ts` checks test files the same way, against each other and the shared homes, and fails a name two shared homes both export (`readyModel` meant two Models once): a different value gets a name that says which (`shopReady` and `SHOP_FRAME_MS`, before the shop went).
- **Effect tests use `it.effect` from `@effect/vitest`.** It runs the test's Effect with a Scope and the TestClock, so time moves only when the test moves it (`TestClock.adjust`, or `settle` and `first` from `@munch/sync-engine/testing` to wait for an event). Use `it.live` only where a test needs real time (a real timer, a real worker, real document events), and say why in the test's name; a network that sleeps runs on the TestClock with `settle`, as sync-engine's engine tests do, and `layer(...)` to share a Layer across a file's tests. A failure to check is `Effect.exit` inside the test. `munch/no-run-in-tests` fails `runPromise`, `runPromiseExit`, `runSync`, `runSyncExit`, `runFork`, and `runCallback` off `Effect`, a `Runtime`, or a runtime of the test's own (`ManagedRuntime.make` too) in test files and their shared setup. Story and Scene tests are `Story.make` and `HtmlScene.make` under `it.effect` ("Tests drive the root through Stories and Scenes"). The Worker's tests run the same way, under Bun (`bun --bun vitest run`), with infra's own `@effect/vitest`.
- **Export only what another module reads, and delete what nothing reads.** `knip` in `bun run lint` fails an unused file, export, exported type, or dependency. An export a module only uses itself loses its `export`. A new entry (a script run with `bun`, a worker, a config) joins its workspace's `entry` list in `knip.jsonc`, and a file another change is editing may sit in `ignoreIssues` with a `TODO`, never for good. Every name a player reads, run modes too, lives in `src/world/names.ts`.
- **No import cycles.** `import/no-cycle` fails a module that imports one that imports it back, type imports too, in the root and `infra` configs. Break one by moving what both need into a module about it (`onlineRun.ts` holds the reads of an online run that the update modules and the drawing share; `src/app/update/dialog.ts` the dialogs' open and close that several handler modules call).
- **A file past 1200 lines holds two jobs**: split it along its section headers into modules with one job each, moving code as it is and adding no barrel. `max-lines` fails it, in `.oxlintrc.json` and infra's config, with no exceptions. State a file's sections share goes in one record passed to them (the balance bot's `BotState`, the audit harness's `HarnessPage`), since an import cannot assign another module's `let`. A split test file's shared setup goes in a `*.fixture.ts` in its `__tests__/` (`boss.fixture.ts`), checked as a test home by `tools/lint/duplicateHelpers.ts`. A new module in `src` goes in its layer's folder ("Folders") and gets its row in that layer's `README.md`: `tools/lint/fileTable.ts` fails a module or stylesheet no table names, and a row naming a file that is gone.

### Git

- Use Conventional Commits, such as `feat: add the shop` or `fix: stop the stick sticking on cancel`.
- Give a commit a body that says what was wrong or missing and what changed.
- Do not add `Co-Authored-By` lines or any AI attribution to a commit message.
- Do not commit or push unless asked.

### Changelog

`CHANGELOG.md` is for players, not developers. Keep it fun and short so it never feels spammy.

- One entry per day that shipped something a player would notice, newest first, headed `## <Month D, YYYY>: <short fun title>`. Add to today's entry instead of starting a second one.
- At most about five bullets a day, each one line with one emoji, saying what changed for the player. Skip refactors, tests, tooling, and anything invisible.
- Goofy and plain, like the game's own copy. No version numbers, commit hashes, or file names.
- When a change ships something players will notice, add or update today's bullet in the same push.

### Waiting on the owner

`TANNER_TODO.md` lists what is blocked on the owner: accounts to set up, decisions, and reviews. When work stops on the owner, add an item there with the exact steps. Remove it once it is done.

### Prose

Do not use em dashes in documentation, comments, or commit messages. Use a period, a comma, or a colon.
