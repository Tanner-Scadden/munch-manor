# Player sync on effect/eventlog

Built November 2026: the design record for moving the player save off `@munch/sync-engine`'s player scope onto Effect's `effect/eventlog` (effect 4.1.4, `node_modules/effect/src/eventlog/`). The spike that proved it is `infra/spike/eventlog/` (read its README first: what passed, what we found, and the save sketch). The owner's decisions: reuse Effect and build only the gaps; the server rejects nothing (no Bones or rank cheat checks); no save migration beyond seeding from what a device has (alpha); the unstable API is fine.

## Scope

- **The player save moves to EventLog**, client and server, with linking by sharing the EventLog identity. The player scope, the Directory, pairing, device keys, and `linked_devices` go.
- **The co-op lobby stays on the scope server** (`room:<code>`, `packages/netcode/src/Lobby.ts`, the GameRoom Durable Object). It needs one authority that refuses a single write (host only, room full, Nightmare locked), and EventLog's server fails a whole batch on a handler failure with no per-entry refusal. That is the wrong tool for an authoritative lobby, so the lobby keeps the scope server and its Replica; `packages/sync-engine` shrinks to what the lobby uses.
- **Room, recording, and matchmaker auth keep their HMAC session token** (`signToken`/`verifyToken`, claims `{deviceId, playerId, expiresMs}`), minted now from the EventLog identity instead of the Directory. `playerId` is the identity's `publicKey`.

## Shared contract (both sides)

- `src/shared/records/sessionApi.ts` (written; read it): `PLAYER_LOG_PATH` (the player socket, `/eventlog?store=player:<publicKey>`), `playerStoreOf`, `SessionRpcs` (`Session.Mint` and `Session.CreateLinkCode`, served on the player socket beside `EventLogRemoteRpcs`), and the HTTP `LINK_REDEEM_PATH` with `RedeemRequest` and `RedeemAnswer`.
- `src/platform/save/playerEvents.ts`: the EventGroups and `PlayerLogSchema = EventLog.schema(...)`. Only `effect` and `src/shared/`, so the Worker imports it.
- `src/platform/save/playerProjection.ts`: `createPlayerTables` (an Effect over `SqlClient` making every projection table, `IF NOT EXISTS`), `PlayerHandlers` (the `EventLog.group(...)` layers for every group, merged), and `readPlayerFacts` (an Effect over `SqlClient` giving `{ unlocked, milestones, marks }` as `syncCore.ts`'s `playerFactsIn` does). Same import limits. The Worker's player Durable Object runs these same handlers into its own SQLite, so the server's projection matches every device's and `/internal/nightmare` reads it.

## Events

Each `PlayerChange` (`src/platform/save/playerSync.ts`) becomes one EventLog write, decided by `changesBetween` as today. Handlers run on every device and the server, in any order, possibly twice (a remote batch's handlers commit before its journal does), so every handler is **order free and idempotent**:

- **Last write wins per field: one `EventRow`** (`node_modules/effect/src/eventlog/EventRow.ts`), a `player` row keyed `"me"`, patched per change: settings (each field flat), rotation, rumble, recordRuns, name, calling, appearance, difficulty chosen and card, onboarding, homeScreenTip, home, lastRun (`EndedRun`), seenPowerUps (`ForgotPowerUps` patches it to empty). Nested structs stay whole where one device changes them at a time; flatten only where two devices plausibly change parts apart (settings).
- **Counted once per entry: an `applied_entries(id TEXT PRIMARY KEY)` guard.** Any handler that adds (`RecordedRun` kills, runs, bests; `EarnedRank`; `GainedMastery`; mission progress) runs only when `INSERT INTO applied_entries ... ON CONFLICT DO NOTHING RETURNING id` returns a row for `entry.id`. Write one helper for it.
- **Merges**: `SawUnlocks`/`SawPowerUps` union; `ReachedRecords` `mergeRunRecords`; bests min/max; `ShelvedProof` first stamp kept (`isEarlierStamp`); `KeptJournal` `addToJournal`; `ClimbedDareLadder` max; missions through `src/shared/records/missionData.ts`'s pure merges; `GrantedVeteranRank` max.
- **Once by key, no balance or rank check**: `BoughtCosmetic` once per id, `PaidRankPurse` once per rank, `EscapedFirst` once per difficulty, `DoubledFirstRun` once per day (a `once_keys(key TEXT PRIMARY KEY)` table, then add), `UnlockedNightmare`, `UnlockedRecording` set.
- **`ChangedDifficulty` never refuses.**
- **`Seeded`**: the whole `PlayerSave`, applied only while the projection holds no save. The first write on a device with no journal: from what the old tables or localStorage hold (the legacy import), or the fresh save.
- Payloads only grow: a new field is optional, nothing is renamed or narrowed (EventRow's rules). This replaces `SAVE_VERSION` for synced data from here on.

## Client (`src/platform/`, `src/app/`)

- `storeSqlite.ts` keeps `PlayerDatabase`'s shape for `store.ts` but runs `EventLog.layer(PlayerLogSchema, PlayerHandlers)` over `SqlEventJournal.layer()` on the same SQLite client (sqlite-wasm-effect, OPFS, one leader tab, followers proxied). Writes go through `EventLog.makeClient(PlayerLogSchema)`, one SQL transaction per save write (`SqlEventJournal` locks with `sql.withTransaction`).
- **Every tab** runs its own `EventLogRemote.layerUnencrypted` socket to the player's store (`RpcClient.layerProtocolSocket` with `retryTransientErrors`, `pingInterval: '60 seconds'`, `RpcSerialization.layerSchemaBinary`, the store `player:<publicKey>` as `EventLog.CurrentStoreId`). The journal drops entries it has by id, and the server drops duplicate writes.
- **Other tabs' and the server's changes**: watch `client.changes` for the projection tables; on a change, read the save and emit `StoreEvent.SyncedSave` only when it differs from the last save this tab wrote or emitted (Schema equivalence).
- **Identity**: `EventLog.makeIdentity` once, kept in the SQLite meta table as `encodeIdentityString`. The old `sync_*` tables, device key, and player scope tables are dropped; the old projection's save, if any, seeds the log once.
- **Sync state**: `SyncState` keeps LocalOnly, Connecting, Synced, Offline; `devices` goes (drop it from the Profile's Account tab, or show nothing in its place).
- **Run settled**: the server rejects nothing, so `RunSettled.Rejected` and `LastRunSync.Rejected` go. `Confirmed` means the run's entry has reached the server (the journal's remote state for it); keep it only if it reads off the journal simply, else drop `awaitSettled` and `LastRunSync` with their Messages and view.
- **Session token** (rooms, recordings): reuse EventLog's own sign-in. Build the remote as `Layer.effect(EventLogRemote.EventLogRemote, EventLogRemote.makeUnencrypted)` over an `EventLogRemoteClient` made by `RpcClient.make(EventLogRemoteRpcs.merge(EventLogCompactionRpcs).merge(SessionRpcs))` (a richer client fits the service), and call `remote.whenAuthenticated(client['Session.Mint']())`; cache the token until near its expiry. `RoomAccess.token` reads it.
- **Linking**: `requestLinkCode` calls `Session.CreateLinkCode({ identity: encodeIdentityString(identity) })` under `whenAuthenticated` and shows the code. `redeemLinkCode` posts `RedeemRequest` to `LINK_REDEEM_PATH`, gets `RedeemAnswer.Redeemed`'s identity string, then stops the remote, deletes the journal and the projection, keeps the new identity, and starts the log again, which replays the store. `LinkProblem` keeps its four cases. `normalizeCode` and `CODE_ALPHABET` move into the client (a small module beside the link flow).
- Delete `playerScope.ts`, `missionScope.ts`, `proofScope.ts`, `masteryScope.ts`, `dareMarkScope.ts`, `playerScopeParts.ts`, `playerMigrations.ts` once nothing reads them. `roomReplica.ts` and `lobbyWrite.ts` stay (the lobby), with `DeviceIdentity` replaced by the session token.

## Server (`infra/worker/`)

- **`PlayerLog` Durable Object**, one per store `player:<publicKey>` (`idFromName(store)`): the spike's `worker.ts` and `doProtocol.ts` (resume on wake, hibernation sockets, schema-binary RPC) made production code, `EventLogServerUnencrypted.layerNoRpcServer(PlayerLogSchema, handlers)` over `SqlEventLogServerUnencrypted.layerStorage()` on `@effect/sql-sqlite-do`, owner-only authorization, the store mapping pinned to its object, `PlayerHandlers` and `createPlayerTables` as its server handlers. Register `EventLog.groupCompaction` where it helps the backlog it sends (optional).
- **Session**: the object's `RpcServer` serves `EventLogRemoteRpcs.merge(SessionRpcs)`. `Session.Mint` reads the client's `EventLogServer.AuthenticatedIdentities` annotation (restored on wake as the spike's handlers do), refuses `NotSignedIn` unless it holds the store's own public key, and mints `signToken({ deviceId: <a per-socket id>, playerId: publicKey, expiresMs })`. So EventLog's Ed25519 sign-in and its key binding are the only proof; no challenge route of our own.
- **Link codes**: `Session.CreateLinkCode` (signed in, and the identity string's public key must be the store's) asks one `LinkCodes` Durable Object (as the Directory was one) for a 6 character code holding the identity string for 10 minutes, one code per player, deleted on redeem. `LINK_REDEEM_PATH` goes to it, tries limited per address with the existing rate limiter (`TooManyTries`).
- **Token module**: `signToken`, `verifyToken`, `SessionClaims`, `mac` move from `packages/sync-engine/src/Identity.ts` into infra (`infra/worker/sessionToken.ts`); rooms, recordings, the matchmaker, and the lobby's `Authenticate` import it there.
- `/internal/nightmare` asks the `PlayerLog` object, which answers from `readPlayerFacts`. GameRoom finds it by `player:<playerId>`.
- **Removed**: the `SyncScope` and `SyncDirectory` objects (Alchemy deletes their classes), `/sync/challenge`, `/sync/session`, `/sync/link*`, `/internal/linked-devices` (`makeChallenge` and `checkChallenge` go too unless the lobby needs them). `/sync/socket?scope=room:*` and `/sync/exchange?scope=room:*` still forward to GameRoom for the lobby.
- **`packages/sync-engine`** drops `Directory`, `Pairing`, `Device`, the identity half of `Identity.ts`, and the browser identity API; it keeps what the lobby uses (Mutation, Protocol, Replica, Rows, Scope, Server, Sync, the transports, Testing, InProcess). `packages/netcode`'s `LobbyClient` takes a token from its caller instead of signing in a device; `tools/mp-dev` gets one by `Session.Mint` with a fresh EventLog identity.
